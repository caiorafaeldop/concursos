ANDROID · ACTIVITY

Os 7 passos da Activity Android

Uma Activity representa uma tela. O sistema operacional chama métodos (callbacks) conforme você abre, alterna ou fecha o app:

Visível ≠ Em foco: em onStart() a tela já aparece, mas só em onResume() ela recebe toques do usuário.
ANDROID · CENÁRIOS REAIS

O que dispara cada pausa?

Regra prática: libere câmera/GPS em onPause() ou onStop(); nunca espere onDestroy() para salvar dados importantes!
PEGADINHA CLÁSSICA

Virou o celular? A tela morre e renasce!

Por padrão, girar o aparelho é uma mudança de configuração. O Android destrói a Activity antiga e cria uma nova do zero para carregar o layout horizontal:

onPause()→ onStop()→ onDestroy()→ onCreate()→ onStart()→ onResume()
Variáveis comuns na Activity somem na rotação! Para sobreviver, use ViewModel (mantém estado em memória na rotação) ou onSaveInstanceState() (Bundle leve se o SO matar o processo).
GERÊNCIA DE MEMÓRIA

Quem o Android mata quando falta RAM?

O Android ordena os processos em 5 níveis de prioridade. Se faltar memória, ele mata de baixo para cima:

PrioridadeTipo de processoRisco de morrer
1 (Maior)Foreground (Activity em onResume)Quase zero (só último caso)
2Visible (Activity visível atrás de diálogo)Muito baixo
3Service (música tocando em segundo plano)Baixo
4Background (app em onStop)Médio/Alto
5 (Menor)Empty / Cached (sem componente ativo)Primeiro a ser morto!
IOS · UIVIEWCONTROLLER

Ciclo de vida de uma tela no iOS

No UIKit (iOS), a tela é gerenciada por uma UIViewController. Os nomes mudam, mas a lógica é irmã gêmea do Android:

viewDidLoad() roda uma única vez quando a view sobe para a memória. Se você precisa atualizar um saldo toda vez que o usuário volta para a tela, use viewWillAppear()!
IOS · ESTADOS DO APP

Os 5 estados do aplicativo iOS

Além da tela individual, o próprio app iOS (UIApplication / SceneDelegate) transita entre 5 estados:

Not RunningApp fechado ou morto pelo sistema.
InactiveEm transição (ex.: ligação ou Control Center aberto).
ActiveEm primeiro plano recebendo eventos.
BackgroundOculto, mas ainda executando código curto.
SuspendedCongelado na RAM; pode ser morto sem aviso.

RESUMO DO CAPÍTULO 1

Para não errar nunca mais

“Criar é 1 vez (onCreate / viewDidLoad); aparecer e pausar acontecem toda hora.” E lembre: girar o Android destrói e recria a Activity — use ViewModel para preservar estado!
  • Activity Android: onCreate → onStart → onResume → onPause → onStop → onDestroy.
  • Volta de onStop passa por onRestart() antes de onStart().
  • Processos Cached/Empty são os primeiros mortos pelo Android; Suspended no iOS também pode ser descartado sem aviso.
  • viewDidLoad = montagem inicial; viewWillAppear = antes de exibir novamente.
TESTE RÁPIDO · CAPÍTULO 1

4 questões no estilo FGV

1. Um pop-up parcial cobre parte da Activity Android sem tirá-la totalmente de vista. Qual callback roda?

Resposta: apenas onPause(). Como a Activity ainda está parcialmente visível, onStop() não é chamado.

2. Ao girar a tela do Android, os dados de um campo sem ViewModel sumiram. Por quê?

Resposta: a rotação altera a configuração e força onDestroy() seguido de novo onCreate(), criando nova instância da Activity.

3. No iOS, onde colocar uma chamada que precisa recarregar dados sempre que o usuário retorna à tela?

Resposta: em viewWillAppear() (ou viewDidAppear()), nunca em viewDidLoad(), que só executa na primeira carga.

4. Qual estado de processo Android tem maior risco de ser encerrado pelo sistema por falta de memória?

Resposta: processos em Cached / Empty (sem componentes ativos), seguidos de Background, enquanto Foreground tem prioridade máxima.

CHAVE-VALOR LEVE

SharedPreferences (Android) e UserDefaults (iOS)

São armazéns simples de pares chave → valor salvos em arquivo XML (Android) ou plist (iOS) dentro da pasta privada do app.

Use para: tema (claro/escuro), idioma escolhido, flag "já viu tutorial", último filtro simples.
NÃO use para: listas grandes, buscas com filtro/JOIN, arquivos binários ou senhas/tokens sem criptografia.
Pegadinha FGV: SharedPreferences não é banco relacional e seus dados ficam em texto claro no XML (acessível em aparelhos com root).
RELACIONAL EMBUTIDO

SQLite puro: poderoso, porém trabalhoso

O SQLite já vem embutido no Android e no iOS. É um banco relacional completo em um único arquivo .db, com suporte a SQL e transações ACID.

// SQLite puro no Android exige SQL manual e Cursor:
Cursor c = db.rawQuery("SELECT * FROM procesoss WHERE id = ?", args);
// Erro de digitação ("procesoss") só explode em RUNTIME!
Com SQLite puro (SQLiteOpenHelper), erros de sintaxe SQL ou nomes de coluna errados só são descobertos quando o app roda e quebra.
ANDROID JETPACK

Room: o escudo em cima do SQLite

O Room não substitui o SQLite — ele é uma camada de abstração (ORM) sobre o SQLite com 3 peças obrigatórias:

Trunfo do Room: verifica suas queries SQL em tempo de compilação, gera boilerplate automático e bloqueia queries na Main Thread por padrão.
ROOM NA PRÁTICA

Exemplo mínimo de @Entity e @Dao

@Entity(tableName = "processos")
data class Processo(@PrimaryKey val numero: String, val classe: String)

@Dao
interface ProcessoDao {
  @Query("SELECT * FROM processos WHERE numero = :n")
  suspend fun buscar(n: String): Processo?  // Coroutine: fora da UI Thread!
}

Se você errar o nome da tabela dentro de @Query, o projeto nem compila. E o suspend garante execução assíncrona sem travar a tela.

FLUTTER / DART · NOSQL

Hive e Isar: velocidade sem SQL

No ecossistema Flutter, dois bancos NoSQL locais muito cobrados são o Hive e o Isar (criados pelo mesmo autor):

📦 Hive

  • Armazena em Boxes (caixas chave-valor binárias).
  • Muito leve e rápido para cache e objetos simples (via TypeAdapter).
  • Limite: não possui índices secundários nem motor de consultas complexas nativo.

⚡ Isar

  • Banco NoSQL de objetos embutido (motor em Rust/C++).
  • Suporta índices compostos, filtros, ordenação e busca textual.
  • Suporta transações ACID, links entre coleções e consultas assíncronas.

PEGADINHA DE PROVA

Migrations e perda de dados

Quando o app atualiza e você adiciona uma coluna nova no banco local (Room/SQLite), o que acontece se não criar uma Migration?

Se você usar fallbackToDestructiveMigration() em produção, o Room apaga todas as tabelas e recria do zero — o usuário perde todos os dados offline! Em produção, escreva a Migration(1, 2) com ALTER TABLE.
RESUMO DO CAPÍTULO 2

Mapa mental da persistência

“Preferência é SharedPreferences; SQL seguro é Room; Flutter rápido com busca é Isar.” Nenhum deles substitui armazenamento criptografado quando o dado é senha ou token!
  • SharedPreferences (Android) e UserDefaults (iOS): chave-valor leve, nunca segredos.
  • Room = @Entity + @Dao + @Database sobre SQLite, com validação em compilação.
  • Hive = caixas chave-valor binárias; Isar = NoSQL com índices, filtros e ACID.
  • Atualizou esquema do banco em produção? Crie Migration explícita.

POR QUE PROTEGER?

O risco do Root, Jailbreak e Backup

Em condições normais, o sistema operacional isola cada app numa Sandbox. Mas esse muro cai quando:

  • O aparelho tem Root (Android) ou Jailbreak (iOS): o atacante lê qualquer arquivo em /data/data/.
  • O manifesto Android deixa android:allowBackup="true": cópias via USB (ADB) podem extrair bancos e preferências.
  • O app foi compilado com android:debuggable="true" em produção: permite acoplar depurador e inspecionar memória.
Nunca confie só na sandbox do SO para guardar tokens de sessão, chaves privadas ou dados pessoais sensíveis!
COFRES OFICIAIS

Android Keystore e iOS Keychain

O Android Keystore impede que a chave criptográfica seja exportada do dispositivo, mesmo que o processo do app seja comprometido.

ENGENHARIA REVERSA

Como um atacante abre seu app?

Um arquivo .apk ou .ipa é basicamente um pacote ZIP. Qualquer pessoa baixa da loja e analisa em minutos:

APK / AAB→ Descompacta (classes.dex)→ jadx / apktool→ Código Java/Kotlin legível!
IPA (iOS)→ Binário Mach-O→ Ghidra / Hopper / class-dump→ Strings e fluxo expostos!
Erro fatal: colocar const API_SECRET = "sk_live_998877" no código. Ferramentas como strings ou jadx acham isso em 5 segundos!
DEFESA EM CAMADAS

O que o R8 / ProGuard faz (e o que NÃO faz)

// Antes do R8 (código original):
class ValidadorAssinatura { fun verificarToken(cpf: String) { ... } }

// Depois do R8 (minificado e ofuscado):
class a { fun a(b: String) { ... } }
O que o R8 faz: renomeia classes/métodos, remove código não usado (shrinking) e dificulta leitura humana.
O que o R8 NÃO faz: não criptografa segredos! Strings constantes como chaves de API continuam visíveis no bytecode.

CASO RESOLVIDO

Onde guardar a chave da API de pagamentos?

Errado: guardar a chave privada da gateway dentro de um arquivo .env empacotado no Flutter ou no BuildConfig do Android.
Certo: o app mobile envia o pedido autenticado para o seu próprio backend; o backend guarda a chave privada no servidor e chama a gateway.

Lembre da regra: tudo que vai para o aparelho do usuário está em território não confiável.

RESUMO DO CAPÍTULO 3

Blindagem mobile em 1 frase

“Segredo de verdade fica no servidor; segredo do usuário vai pro Keystore/Keychain.” R8/ProGuard atrasa o atacante, mas não transforma o celular em cofre impenetrável.
  • Use Android Keystore (+ EncryptedSharedPreferences / SQLCipher) e iOS Keychain.
  • Desative allowBackup e debuggable no build de produção.
  • R8/ProGuard ofusca nomes e reduz APK, mas nunca protege chaves hardcoded.
  • Valide integridade do app e do dispositivo (Play Integrity / App Attest).

TLS/SSL e SSL Pinning na Rede

🛡️
1. TLS/SSL (HTTPS)Como o cadeado funciona na prática.
2. A brecha das CAsPor que um proxy MitM ainda espiona.
3. SSL PinningFixando certificado ou chave pública.
4. SPKI & BackupComo não travar o app na renovação.
🪪
TLS padrão é aceitar qualquer pessoa que tenha um crachá assinado por um dos 100 cartórios do celular. SSL Pinning é dizer: "Eu só abro a porta para quem tiver exatamente esta digital!"
TRANSPORTE SEGURO

O que o TLS/SSL garante?

O TLS (sucessor moderno do SSL) protege a comunicação entre o app e a API contra escuta e adulteração na rede (Wi-Fi público, 4G, roteadores):

  • Confidencialidade: ninguém no meio lê o payload JSON (criptografia simétrica de sessão).
  • Integridade: qualquer byte alterado no caminho quebra a verificação (MAC/AEAD).
  • Autenticidade do servidor: o servidor apresenta um Certificado Digital X.509 assinado por uma CA confiável.
No handshake TLS, a criptografia assimétrica autentica e negocia a chave; depois a troca de dados usa criptografia simétrica por ser muito mais rápida.
O PROBLEMA

Por que o TLS padrão não basta contra MitM?

O celular confia em dezenas de Autoridades Certificadoras (CAs) pré-instaladas. Se o usuário ou um malware instalar uma CA extra (como um proxy Burp Suite / Charles), o ataque Man-in-the-Middle passa sem erro!

A SOLUÇÃO

SSL Pinning (Certificate Pinning)

Com SSL Pinning, o aplicativo carrega dentro dele a "impressão digital" esperada do servidor. Mesmo que o aparelho tenha uma CA maliciosa instalada, a conexão é recusada na hora!

QUAL PIN ESCOLHER?

Certificado inteiro × Chave Pública (SPKI)

Tipo de PinComo funcionaImpacto na renovação
Certificado X.509 inteiroFixa o arquivo/hash do certificado exato.Quando o certificado vence (ex.: 1 ano), o app antigo para de funcionar até atualizar!
Chave Pública (SPKI)Fixa o hash SHA-256 da chave pública do servidor.Você renova o certificado mantendo o mesmo par de chaves e o app continua funcionando!
Recomendação oficial: prefira fixar o hash SHA-256 da chave pública (SPKI) e sempre configure pelo menos 1 pin de backup (chave reserva).
IMPLEMENTAÇÃO ANDROID

Configuração declarativa no Android

Desde o Android 7 (API 24), não é preciso escrever código complexo de socket: basta usar network_security_config.xml:

<network-security-config>
  <domain-config cleartextTrafficPermitted="false">
    <domain includeSubdomains="true">api.tjpb.jus.br</domain>
    <pin-set expiration="2027-01-01">
      <pin digest="SHA-256">7HIpactkIAq2Y49orFOOQKurWxmmSFZhBCoQYcRhJ3Y=</pin>
      <pin digest="SHA-256">backupPinReservaHashAqui1234567890abcdef=</pin>
    </pin-set>
  </domain-config>
</network-security-config>

No iOS, implementa-se via URLSessionDelegate (verificando a chave pública no didReceive challenge) ou bibliotecas como TrustKit.

PEGADINHA DA BANCA

O risco de "brickar" (travar) o app

Se o servidor trocar o certificado e a chave privada sem que o app tenha um pin de backup (ou sem atualização prévia nas lojas), 100% dos usuários ficarão sem conexão!

Outro ponto: em builds de produção, cleartextTrafficPermitted deve ser false para impedir fallback acidental para HTTP sem criptografia.

AVISO IMPORTANTE

Pinning substitui TLS? Não!

Errado: "Como uso SSL Pinning, não preciso de HTTPS/TLS."
Certo: SSL Pinning é uma camada extra de validação em cima do handshake TLS para restringir em quem o app confia.

E lembre: no celular com root, um atacante pode tentar remover o pinning em memória (ex.: Frida), por isso segurança mobile é sempre em camadas.

RESUMO DO CAPÍTULO 4

Checklist de rede segura

“TLS fecha o túnel; SSL Pinning escolhe quem tem a chave da porta.” Fixe o hash SHA-256 da chave pública (SPKI) + 1 pin de backup + bloqueie HTTP em texto claro.
  • TLS garante confidencialidade, integridade e autenticidade via CA.
  • SSL Pinning barra ataques MitM mesmo com CA de proxy instalada no aparelho.
  • Pinning de SPKI sobrevive à renovação do certificado (se mantiver a chave).
  • No Android, use network_security_config.xml com cleartextTrafficPermitted="false".

4 questões no estilo FGV

Resposta: permite renovar o certificado no servidor sem quebrar versões antigas do app, desde que o par de chaves seja mantido.

Consumo de APIs REST/JSON e Push (FCM)

🚀
1. REST & JSONVerbos HTTP, status codes e serialização.
2. Main Thread & ANRPor que rede sempre roda assíncrona.
3. Arquitetura FCMComo o Push chega até o celular.

🍕
REST é você ligar na pizzaria e pedir (o app puxa dados quando quer). Push (FCM) é a campainha tocar quando o entregador chega (o servidor avisa o app sem você ficar perguntando).
APIS REST NO MOBILE

Verbos HTTP e Status Codes essenciais

CódigoSignificadoAção típica do app mobile
200 / 201OK / CreatedDesserializa JSON e atualiza a tela.
400Bad RequestExibe erro de validação do formulário.
401UnauthorizedToken ausente/expirado → tenta refresh token ou login.

PUT substitui o recurso inteiro; PATCH atualiza apenas os campos enviados (economiza dados móveis 4G/5G!).
DESEMPENHO & RESILIÊNCIA

Nunca bloqueie a Main Thread (UI Thread)!

A Main Thread desenha os quadros da tela (60/120 fps) e responde aos toques. Fazer rede ou parse pesado de JSON nela congela o aplicativo:

Na Main Thread: tela congela; após ~5 segundos sem resposta, o Android dispara o erro fatal ANR (Application Not Responding).
Assíncrono: use Coroutines / Flow (Kotlin), async/await (Swift) ou Future / Isolate (Flutter) + timeouts curtos e cache local.
PUSH NOTIFICATIONS

Como funciona o FCM por dentro?

O app não fica com uma conexão HTTP aberta o tempo todo (acabaria com a bateria). Ele usa o canal único do sistema via Firebase Cloud Messaging (FCM):

Registration Token: identifica a instalação do app. Pode mudar (reinstalação, limpeza de dados) — por isso implemente onNewToken() para atualizar no backend.

O CORAÇÃO DO FCM

Notification Message × Data Message

Essa é a diferença mais cobrada em provas sobre Push Notification no Android:

Tipo de MensagemApp em Foreground (aberto)App em Background / Fechado
Notification Message
(campo notification)		Chama onMessageReceived() do app.O Sistema Operacional exibe direto na bandeja! Seu código onMessageReceived NÃO roda.
Data Message
(apenas campo data)		Chama onMessageReceived() do app.Sempre chama onMessageReceived() do seu app (ideal para sync silencioso ou alerta customizado).
EXEMPLO DE PAYLOAD FCM

Olhando o JSON enviado ao FCM

// Notification Message (SO exibe em bg):
{
  "token": "fcm_token_abc...",
  "notification": {
    "title": "Intimação",
    "body": "Novo despacho no PJe"
  }
}
// Data Message (App sempre trata):
{
  "token": "fcm_token_abc...",
  "data": {
    "tipo": "sync_processo",
    "id": "0801234-55"
  }
}
Se você mandar os dois blocos juntos (notification + data) e o app estiver em background, o SO exibe a notificação e os dados extras só chegam nos extras da Intent quando o usuário clicar nela!
BOAS PRÁTICAS DE REDE

Paginação, Cache e Backoff Exponencial

  • Paginação: nunca baixe 10.000 processos num único JSON; use cursor ou page/size.
  • Timeout & Retry: defina timeout explícito; ao tentar de novo após erro 503/429, use backoff exponencial (1s → 2s → 4s) para não derrubar o servidor.
  • Offline-first: mostre primeiro o cache local (Room/Isar) e atualize em segundo plano quando a API responder.
TÓPICOS NO FCM

APIs e Push sem mistério

“Rede fora da Main Thread (sem ANR); FCM Data Message sempre aciona o código do app.” 401 = falta autenticação (renovar token); 403 = sem permissão.
  • Operações HTTP e JSON rodam assíncronas (Coroutines/async-await) para evitar ANR.
  • Use PATCH para atualizações parciais e paginação para listas grandes.
  • Atualize o FCM Token no backend via onNewToken().
  • Notification = SO exibe em background; Data = onMessageReceived() sempre roda.
TESTE RÁPIDO · CAPÍTULO 5

4 questões no estilo FGV

1. O que acontece se um app Android fizer uma requisição HTTP síncrona demorada na Main Thread?

Resposta: a interface trava e o sistema dispara um erro de ANR (Application Not Responding) após cerca de 5 segundos.

2. Qual a diferença prática entre os status HTTP 401 e 403 ao consumir uma API REST?

Resposta: 401 (Unauthorized) significa que o usuário não está autenticado ou o token expirou; 403 (Forbidden) significa que está autenticado, mas não tem permissão para aquele recurso.

3. No FCM, qual tipo de mensagem garante que onMessageReceived() execute mesmo com o app em segundo plano?

Resposta: Data Message (payload enviado apenas no campo data, sem o bloco notification).

4. Por que o app deve enviar o token FCM ao servidor dentro de onNewToken()?

Resposta: porque o token de registro pode ser rotacionado ou gerado novamente pelo Firebase/SO ao longo do ciclo de vida da instalação.
