LINHA DO TEMPO

Em que versão cada recurso ficou final?

Antes de virar final, quase tudo passa por versões preview (precisam de --enable-preview). Records foram preview no 14 e 15 → final no 16. Sealed: preview 15 e 16 → final no 17. Virtual threads: preview 19 e 20 → final no 21. “Records surgiram no Java 14” é meia-verdade: ali eram só preview.

STREAMS

A esteira: fonte → intermediárias → terminal

List<Integer> r = List.of(1, 2, 3, 4, 5, 6).stream()
    .filter(n -> n % 2 == 0)
    .map(n -> n * n)
    .toList();
System.out.println(r);

Stream.of("a", "b").peek(System.out::println);  // sem terminal: NÃO imprime nada
[4, 16, 36]
Intermediárias (filter, map, flatMap, sorted, distinct, limit, peek) são lazy; nada executa até uma operação terminal (collect, toList, forEach, reduce, count, findFirst, anyMatch). O Stream não altera a coleção de origem.

RECORDS (FINAL NO JAVA 16)

Classe de dados em uma linha

antes: classe “na mão”

final class Ponto {
  private final int x, y;
  Ponto(int x, int y) { this.x = x; this.y = y; }
  int getX() { return x; }
  int getY() { return y; }
  // + equals, hashCode, toString...
}

record

record Ponto(int x, int y) {
  Ponto {                // construtor compacto
    if (x < 0) throw new
      IllegalArgumentException();
  }
}
var p = new Ponto(1, 2);
System.out.println(p);                        // Ponto[x=1, y=2]
System.out.println(p.x());                    // 1   (acessor x(), não getX())
System.out.println(p.equals(new Ponto(1, 2)));// true (compara os componentes)
Record gera campos private final, construtor canônico, acessores, equals, hashCode e toString. É implicitamente final, estende java.lang.Record (logo não estende outra classe), pode implementar interfaces, pode ter métodos e campos static, mas não campos de instância extras. A imutabilidade é rasa: um componente List mutável continua mutável.
SEALED (17) + SWITCH COM PADRÕES (21)

Hierarquia fechada + switch que confere tudo

sealed interface Forma permits Circulo, Quadrado {}
record Circulo(double r) implements Forma {}
record Quadrado(double lado) implements Forma {}

static double area(Forma f) {
  return switch (f) {
    case Circulo c          -> Math.PI * c.r() * c.r();
    case Quadrado(double l) -> l * l;          // record pattern
  };                                           // sem default: o compilador sabe que é exaustivo
}
area(new Quadrado(3));                         // 9.0
Subclasse permitida de um tipo sealed deve ser final, sealed ou non-sealed (records já são final). No switch com padrões é possível usar guarda: case Integer i when i > 10 -> ... e case null.
VIRTUAL THREADS (FINAL NO JAVA 21)

Muitas threads leves sobre poucas threads do SO

try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
  for (int i = 0; i < 10_000; i++)
    ex.submit(() -> { Thread.sleep(1000); return 1; });
}   // close() espera todas: termina em ~1 s, não em 10.000 s
Thread.ofVirtual().start(() -> System.out.println("oi"));
✓ Ganham em vazão para tarefas que esperam I/O (banco, HTTP). ✗ Não deixam código CPU-bound mais rápido. ✗ Não se faz pool de virtual threads: cria-se uma por tarefa. No Java 21, bloquear dentro de synchronized pode “prender” (pinning) a carrier.
RESUMO

O que levar para a prova

Pergunta mágica: “Isso é final em que versão, e o que ele gera/exige?”records 16 · sealed 17 · switch com padrões, record patterns e virtual threads 21 · lambdas e Streams 8.
  • Map não é Collection; TreeSet/TreeMap ordenam; HashSet não garante ordem.
  • List.of imutável e sem null; Arrays.asList tamanho fixo.
  • Interface funcional = 1 método abstrato; variáveis capturadas efetivamente finais.
  • Stream: lazy, usado uma vez, só executa com operação terminal.
  • Record: final, acessor x(), equals/hashCode/toString gerados, pode implementar interface.
  • Sealed + permits; filhas final/sealed/non-sealed; switch exaustivo sem default.
  • Virtual threads: para I/O, uma por tarefa, sem pool.
TESTE RÁPIDO

Estilo FGV: resolva antes de abrir

1. Qual a saída de Stream.of(3,1,2).sorted().map(n -> n*10).toList()?

[10, 20, 30]. sorted ordena (1,2,3) e map multiplica cada um. A lista resultante não é modificável.

2. “Um record pode estender uma classe abstrata própria do sistema.” Certo ou errado?

Errado. Todo record já estende java.lang.Record e Java não tem herança múltipla de classes. Ele pode, porém, implementar interfaces.

3. Uma classe que estende uma classe sealed sem declarar final, sealed ou non-sealed compila?

Não. A subclasse permitida é obrigada a escolher um dos três modificadores (records e enums já são implicitamente finais).

4. Um serviço CPU-bound (cálculo pesado) ficará mais rápido trocando threads de plataforma por virtual threads?

Não. Virtual threads aumentam a vazão de tarefas que passam o tempo esperando I/O. O trabalho de CPU continua limitado ao número de núcleos.

JPA: ENTIDADE E ESTADOS

Uma classe vira tabela; o EntityManager cuida dela

@Entity @Table(name = "processo")
public class Processo {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;
  @Column(nullable = false, unique = true) private String numero;
  protected Processo() {}            // JPA exige construtor sem argumentos
}
Entidade gerenciada está no contexto de persistência (cache de 1º nível): alterar um campo dela gera UPDATE no flush/commit sem chamar nenhum método (dirty checking). find busca já; getReference pode devolver um proxy preguiçoso.
RELACIONAMENTOS E N+1

Quem é o dono, o que carrega junto e o problema N+1

@Entity class Vara {
  @OneToMany(mappedBy = "vara")
  List<Processo> processos;   // lado inverso
}
@Entity class Processo {
  @ManyToOne @JoinColumn(name="vara_id")
  Vara vara;                  // lado dono (tem a FK)
}
AnotaçãoFetch padrão
@ManyToOne · @OneToOneEAGER
@OneToMany · @ManyToManyLAZY

✗ N+1

varas = "SELECT v FROM Vara v"   // 1 consulta
for (v : varas) v.getProcessos().size(); // +N

✓ JOIN FETCH

"SELECT DISTINCT v FROM Vara v
   JOIN FETCH v.processos"       // 1 consulta
Acessar uma coleção LAZY depois que o contexto fechou gera LazyInitializationException (Hibernate). A solução não é pôr tudo EAGER: é buscar o necessário com JOIN FETCH ou @EntityGraph. TESTE RÁPIDO

Estilo FGV: resolva antes de abrir

1. Um método @Transactional lança IOException (checked). Sem configuração extra, o que acontece?

Commit. Por padrão o Spring só faz rollback em exceções não verificadas (RuntimeException) e Error. Para checked, use rollbackFor = IOException.class.

2. Num relacionamento bidirecional Vara 1–N Processo, onde vai o mappedBy?

No lado inverso, o @OneToMany em Vara. O dono é Processo, que possui a chave estrangeira (@ManyToOne/@JoinColumn).

3. Qual anotação liga /processos/7 ao parâmetro Long id?

@PathVariable. @RequestParam pega a query string (?id=7); @RequestBody desserializa o corpo.

4. “Hibernate e JPA são sinônimos.” Certo ou errado?

Errado. JPA (Jakarta Persistence) é a especificação; Hibernate é uma implementação dela, com recursos próprios além do padrão. EclipseLink é outra implementação.

Closure: a função leva a “mochila” do escopo

function contador() {

Arrow não tem this próprio

const timer = {
  seg: 0,
  iniciar() {
    setTimeout(function () {
      console.log(this.seg); // undefined
    });
    setTimeout(() =>
      console.log(this.seg)); // 0
  }
};
timer.iniciar();
Closure: a função interna continua acessando as variáveis do escopo onde foi criada, mesmo depois que a função externa terminou. Arrow function não tem this nem arguments próprios e não pode ser usada com new; o this vem do escopo ao redor (léxico).

  • const não congela objeto. === não converte tipos.
  • Falsy: false, 0, -0, 0n, "", null, undefined, NaN. ?? só troca null/undefined.
  • Arrow function: this léxico. Closure lembra o escopo de criação.
  • Promise.all falha na 1ª rejeição; allSettled espera todas.
  • TS: estrutural, tipos apagados; unknown exige narrowing.
  • Node: 1 thread de JS + libuv; ótimo para I/O, ruim para CPU pesada.

Estilo FGV: resolva antes de abrir

1. Saída de: console.log(1); setTimeout(()=>console.log(2)); Promise.resolve().then(()=>console.log(3)); console.log(4);

1 4 3 2. Primeiro o síncrono (1, 4), depois a microtarefa da Promise (3), por fim a tarefa do setTimeout (2).

5 e 0. || substitui qualquer falsy (0 é falsy); ?? só substitui null ou undefined.

Porque o JavaScript roda numa única thread do event loop; enquanto ela calcula, nenhum callback é atendido. Solução: worker_threads, processos separados ou outro serviço.

REACT: ESTADO

As duas pegadinhas de estado

✗ soma só 1

function mais2() {

  setN(n + 1);   // n ainda é 0
}                // resultado: 1

✓ soma 2

function mais2() {
  setN(c => c + 1);
  setN(c => c + 1);
}                // resultado: 2

✗ tela não atualiza

✓ novo array

O valor de n é uma “foto” daquela renderização; setN não muda a variável na hora, agenda a atualização (e o React agrupa várias, o batching). Use a forma funcional quando o novo valor depende do anterior e nunca mute o estado: crie objetos/arrays novos.
