CONCEITO BASE

UI não é UX — e uma precisa da outra

UX (User Experience) abrange toda a percepção e resposta do usuário antes, durante e após interagir com o sistema. UI (User Interface) é a camada visual e interativa por onde essa interação acontece.
PRINCÍPIOS DE UI

Como o olho lê uma tela sem esforço

Uma tela boa guia o olhar como placas numa rodovia: você sabe o que é título, o que é botão e o que pertence ao mesmo grupo.

4 pilares visuais de UI

  • Hierarquia visual: o mais importante é maior, mais escuro ou mais destacado.
  • Proximidade e agrupamento: itens relacionados ficam perto (Lei da Proximidade).
  • Contraste e legibilidade: texto se separa claramente do fundo.
  • Consistência e feedback: botão parecido faz ação parecida e responde ao clique.

Exemplo prático

Botão primário cheio ("Enviar") + secundário discreto ("Cancelar").

USABILIDADE

Heurísticas de Nielsen que mais caem em prova

Jakob Nielsen listou 10 heurísticas de usabilidade. Estas 5 são campeãs de cobrança em concursos:

HeurísticaPergunta simplesExemplo no sistema

CAMINHO DO USUÁRIO

User Flow: o mapa antes de desenhar telas

Antes de abrir ferramenta de desenho, traçamos o User Flow: cada passo, decisão e saída (inclusive de erro) para cumprir um objetivo.

Por que importa? User Flow descobre becos sem saída (ex.: senha errada sem link de recuperação) enquanto mudar ainda custa zero linhas de código.

PEGADINHA

Onde a banca FGV tenta derrubar

1. Wireframe × Protótipo: se a questão disser que o artefato é "esqueleto estático em baixa fidelidade para validar estrutura sem cores", é wireframe. Se falar em "simulação clicável de navegação e testes de fluxo", é protótipo.
2. UI × UX: trocar UI por UX. Deixar um botão bonito é UI; reduzir passos de 8 para 3 e evitar erro de preenchimento é UX.
Protótipo pode ser até em baixa fidelidade (telas clicáveis simples), desde que permita simular a interação.
Mockup não é clicável — é uma "foto" estática do visual final.
RESUMO

O que você precisa levar deste capítulo

“Fluxo primeiro, esqueleto depois, visual por último — e teste antes de codar.” User Flow → Wireframe → Mockup → Protótipo clicável.
  • UI = visual e controles; UX = jornada e facilidade de uso completa.
  • Nielsen: status visível, consistência, prevenção de erros, reconhecimento e saída fácil.
  • User Flow: mapeia entrada, decisões, caminho feliz e caminhos de erro.
  • Wireframe: baixa fidelidade e estático; Protótipo: interativo.
TESTE RÁPIDO

4 questões no estilo FGV

1. Qual artefato foca em layout e hierarquia sem cores nem interatividade?

Wireframe. Ele funciona como a planta baixa da tela, evitando discussões prematuras sobre estética.

2. Exibir "Salvando rascunho..." durante uma edição atende a qual heurística de Nielsen?

Visibilidade do status do sistema. O usuário sabe em tempo real o que o sistema está fazendo.

3. Usar lista de opções em vez de obrigar o usuário a decorar códigos de comarca aplica qual heurística?

Reconhecimento em vez de memorização. Reduz a carga cognitiva mostrando as escolhas disponíveis.

4. Qual a diferença central entre Mockup e Protótipo?

O mockup é uma representação visual estática; o protótipo é interativo/clicável e simula o fluxo.

DESIGN SYSTEM

O que tem dentro de um Design System de verdade

Design Tokens são variáveis nomeadas que guardam decisões visuais (cor, tipografia, espaçamento) de forma reutilizável entre design (Figma) e código (CSS/Android/iOS).
ATOMIC DESIGN

Atomic Design (Brad Frost): montando em 5 níveis

⚛️ Átomos
button, input, label→ 🧪 Moléculas
barra de busca→ 🦠 Organismos
header completo→ 📐 Templates
esqueleto da página→ 📄 Páginas
conteúdo real
Macete: Átomo não se divide sem perder sentido; Molécula junta 2+ átomos numa função simples; Organismo forma uma seção inteira da interface.
RESPONSIVIDADE

Os 3 ingredientes do Design Responsivo

Um único HTML e CSS se adapta como água no copo: muda de forma conforme o tamanho da tela.

1. Grid fluidoLarguras em %, fr (CSS Grid) ou Flexbox, não em px fixos.
2. Mídia flexívelimg { max-width: 100%; height: auto; } evita estourar a tela.
3. Media Queries@media aplica regras conforme largura/orientação.
Responsivo × Adaptativo: o responsivo flui continuamente para qualquer largura; o adaptativo entrega layouts pré-definidos para pontos fixos (ex.: 320px, 768px, 1280px).
MOBILE-FIRST

Mobile-First vs. Desktop-First no CSS

CritérioMobile-First (Recomendado)Desktop-First
Ponto de partidaTela pequena (celular)Tela grande (monitor)
Media Query@media (min-width: ...)@media (max-width: ...)
EstratégiaProgressive Enhancement (adiciona aos poucos)Graceful Degradation (vai cortando/escondendo)
VantagemForça priorizar o essencial e carrega mais leveÚtil ao adaptar sistema legado gigante
CÓDIGO REAL

Como o CSS Mobile-First funciona na prática

/* 1. Base (Mobile): 1 coluna, sem media query */
.grid { display: grid; grid-template-columns: 1fr; gap: 12px; }

/* 2. Tablet em diante: cresce com min-width */
@media (min-width: 768px) {
  .grid { grid-template-columns: repeat(2, 1fr); }
}

/* 3. Desktop: 3 colunas */
@media (min-width: 1024px) {
  .grid { grid-template-columns: repeat(3, 1fr); }
}
Repare que o celular nem precisa processar as regras de 768px e 1024px — ele já nasce pronto no estilo base!
DETALHES QUE IMPORTAM

Viewport meta tag e área de toque

Sem a meta tag viewport, o navegador mobile finge ter ~980px e encolhe tudo até ficar ilegível:

<meta name="viewport" content="width=device-width, initial-scale=1">
Usar unidades relativas (rem, em, %, vw) e botões fáceis de tocar com o dedo.
Travar zoom com user-scalable=no (quebra acessibilidade para baixa visão!).
PEGADINHA

Armadilhas clássicas da FGV

1. min-width × max-width: Mobile-First usa min-width (de X para cima). Se a questão mostrar max-width decrescente, é Desktop-First!
2. Design System ≠ só biblioteca visual: envolve tokens + componentes + diretrizes de uso e acessibilidade + governança.
3. Esconder conteúdo no mobile: display: none não impede o download de imagens pesadas e pode prejudicar quem usa só o celular.
RESUMO

O que você precisa levar deste capítulo

“Mobile-First começa pequeno com min-width; Design System padroniza tudo com tokens e componentes.” Progressive enhancement + fonte única de verdade.
  • Design System: tokens + componentes + padrões + documentação.
  • Atomic Design: Átomos → Moléculas → Organismos → Templates → Páginas.
  • Responsivo: grid fluido + mídia flexível + media queries + meta viewport.
  • Mobile-First: base mobile + @media (min-width: ...).
TESTE RÁPIDO

4 questões no estilo FGV

1. Qual característica define o uso de Design Tokens em um Design System?

São variáveis semânticas (cor, fonte, espaçamento) compartilhadas entre ferramentas de design e código para garantir consistência.

2. No Atomic Design, um formulário de login completo (header + campos + botão) costuma ser classificado como:

Organismo (combinação de moléculas e átomos formando uma seção funcional completa).

3. Por que não devemos usar user-scalable=no na meta tag viewport?

Porque impede o usuário de dar zoom, violando critérios de acessibilidade para pessoas com baixa visão.

4. Um CSS que define layout de 3 colunas na raiz e usa @media (max-width: 600px) para virar 1 coluna é:

Desktop-First (parte da tela maior e usa max-width para adaptar para baixo).

OS 4 PRINCÍPIOS

POUR: as 4 perguntas da WCAG

WCAG (Web Content Accessibility Guidelines, da W3C/WAI) organiza seus critérios em 4 Princípios (POUR) → Diretrizes → Critérios de Sucesso testáveis (níveis A, AA, AAA).
POUR NA PRÁTICA

Como saber qual princípio foi violado?

Problema encontrado na telaPrincípio violadoPor quê?
Imagem informativa sem atributo altPerceptívelUsuário cego não consegue perceber a informação
Menu só abre passando o mouse (sem Tab/Enter)OperávelQuem usa só teclado não consegue operar o controle
Mensagem “Erro inválido” sem dizer onde nem como corrigirCompreensívelUsuário não entende o que fazer para corrigir
Componente customizado sem role/nome acessívelRobustoTecnologia assistiva não interpreta o componente
NÍVEIS A, AA, AAA

Os 3 degraus de conformidade (são cumulativos!)

Regra de prova: não existe "cumprir AA sem cumprir A". Os níveis são cumulativos. E o padrão exigido na maioria das legislações e editais é o nível AA.
CONTRASTE

Números de contraste que você precisa saber

Na WCAG, o contraste mede a diferença de luminância entre texto e fundo (vai de 1:1 até 21:1):

Tipo de textoNível AANível AAA
Texto normalMínimo 4,5 : 1Mínimo 7 : 1
Texto grande (≥18pt ou ≥14pt negrito)Mínimo 3 : 1Mínimo 4,5 : 1
Texto escuro #1f2430 no fundo branco: contraste alto, fácil de ler.
Texto cinza claro no fundo branco: falha no contraste AA!
WCAG 2.1 → 2.2

O que a WCAG 2.2 trouxe de novidade?

A WCAG 2.2 manteve os 4 princípios POUR e quase toda a base da 2.1, adicionando critérios para mobilidade, baixa visão e cognição:

  • Foco não obscurecido: quando você aperta Tab, uma barra fixa/cookie não pode esconder o elemento focado.
  • Aparência do foco: o contorno de foco precisa ser bem visível.
  • Tamanho mínimo de alvo: botões e links não podem ser minúsculos e colados uns nos outros.
  • Movimentos de arrastar: ações de arrastar devem ter alternativa de clique simples.
  • Entrada redundante e autenticação acessível: não exigir redigitar dados já informados no mesmo fluxo nem obrigar testes cognitivos (como quebra-cabeças) sem alternativa.

Nota de precisão: para a numeração exata de cada critério e suas exceções, confira o texto oficial da W3C (WCAG 2.1 / 2.2).

EXEMPLO PRÁTICO

Cor sozinha nunca pode carregar informação

Se um campo com erro ficar só com borda vermelha, quem tem daltonismo ou usa leitor de tela não percebe o erro:

Borda vermelha sozinha, sem ícone nem mensagem de texto.
Borda vermelha + ícone ⚠ + texto claro: “CPF inválido: informe 11 dígitos”.
Esse cuidado atende ao princípio Perceptível (não depender só de cor) e Compreensível (identificar e ajudar a corrigir o erro).
PEGADINHA

Pegadinhas da FGV sobre WCAG

1. "Todo site público deve cumprir nível AAA": FALSO! A própria W3C reconhece que o nível AAA não é viável para todo tipo de conteúdo. O padrão usual de referência é o AA.
2. "WCAG 2.2 substituiu POUR": FALSO! Os 4 princípios POUR continuam idênticos.
3. Trocar contraste AA por AAA: texto normal no AA é 4,5:1 (e texto grande 3:1). 7:1 é AAA.
RESUMO

O que você precisa levar deste capítulo

“POUR guia o porquê; AA é a meta oficial; 4,5:1 é o contraste padrão.” Perceptível · Operável · Compreensível · Robusto.
  • Perceptível (ver/ouvir), Operável (teclado/foco), Compreensível (claro/previsível), Robusto (leitor de tela).
  • Níveis cumulativos: A ⊂ AA ⊂ AAA (AA = referência regulatória).
  • Contraste AA: 4,5:1 (texto normal) e 3:1 (texto grande).
  • WCAG 2.2 reforçou foco visível/não encoberto, alvo de toque, entrada redundante e login acessível.
TESTE RÁPIDO

4 questões no estilo FGV

1. Um vídeo institucional publicado sem legendas nem audiodescrição fere qual princípio POUR?

Perceptível. Pessoas surdas ou cegas precisam de alternativas para perceber o conteúdo em áudio/vídeo.

2. Se uma página atende ao nível AA da WCAG, ela também atende ao nível A?

Sim. A conformidade da WCAG é cumulativa: AA exige cumprir todos os critérios de nível A e AA.

3. Qual é a razão mínima de contraste exigida no nível AA para texto normal?

4,5:1 (e 3:1 para texto grande).

4. Um cabeçalho fixo que tampa o botão quando o usuário navega com Tab viola qual preocupação da WCAG 2.2?

Foco não obscurecido (Focus Not Obscured), pois o elemento focado pelo teclado precisa continuar visível.

NAVEGAÇÃO RÁPIDA

Skip links e atalhos padronizados no eMAG

Imagine ter que apertar Tab 40 vezes em toda página só para passar pelo menu antes de ler uma notícia. O skip link resolve isso no primeiro Tab!

<body>
  <!-- Primeiro elemento focável da página -->
  <a class="skip-link" href="#conteudo-principal">
    Ir para o conteúdo principal
  </a>
  <nav aria-label="Menu principal">...</nav>
  <main id="conteudo-principal" tabindex="-1">...</main>
</body>
O eMAG recomenda barra de acessibilidade no topo com links diretos e atalhos de teclado padrão para conteúdo, menu, busca e rodapé (confira os números exatos no manual oficial do eMAG).

Boas práticas de Conteúdo que evitam erros

PEGADINHA

Pegadinhas da FGV sobre eMAG

1. "Nota 100% no ASES garante portal 100% acessível": FALSO! Um alt="imagem123.jpg" passa no robô, mas é inútil para o usuário cego. Teste manual é obrigatório.
2. "eMAG proíbe JavaScript": FALSO! O eMAG aceita JS, desde que a interface continue operável pelo teclado e acessível (seção Comportamento).
3. "Usar tabela para alinhar menu e formulário": FALSO! Tabelas são só para dados tabulares; layout usa CSS (Grid/Flexbox).

TESTE RÁPIDO

4 questões no estilo FGV

1. Qual é a relação correta entre WCAG e eMAG?

O eMAG é o modelo brasileiro de acessibilidade em governo eletrônico, baseado nas diretrizes internacionais da WCAG e adaptado aos portais públicos.

2. Por que o texto de link "Clique aqui" viola boas práticas do eMAG?

Porque usuários de leitores de tela costumam navegar pela lista de links isolados; "Clique aqui" não informa o destino nem a ação.

3. Um validador automático verifica se a descrição do atributo alt está semanticamente correta?

Não. Ele verifica apenas se o atributo existe; julgar se o texto descreve bem a imagem exige avaliação humana.

4. Para que serve o link "Ir para o conteúdo principal" no topo de um portal?

Para permitir que usuários de teclado e leitores de tela pulem blocos repetitivos de cabeçalho e menu.

PRIMEIRA REGRA DA ARIA

HTML nativo sempre ganha da ARIA

1ª Regra da WAI-ARIA: se você pode usar um elemento HTML nativo com a semântica e o comportamento já prontos (como <button> ou <a href>), use o nativo em vez de adaptar uma <div> com ARIA.

✗ Jeito frágil

<div role="button" onclick="salvar()">
  Salvar
</div>

Não recebe foco via Tab e não dispara com Enter ou Espaço!

✓ Jeito certo

<button type="button" onclick="salvar()">
  Salvar
</button>

Já entra no Tab, anuncia “botão Salvar” e aceita Enter/Espaço.

FOCO E TECLADO

tabindex e Regiões Vivas sem mistério

tabindex="0"Entra na ordem natural do Tab (ordem do DOM).
tabindex="-1"Não entra no Tab, mas recebe foco via JS (el.focus()).
tabindex > 0Evite! Bagunça a ordem natural de navegação.
aria-live="polite" × "assertive": polite espera o leitor terminar a frase atual (ideal para "Salvo com sucesso"); assertive interrompe na hora (só para alertas urgentes).
PEGADINHA

3 erros graves que a FGV adora cobrar

1. "ARIA cria comportamento de teclado": FALSO! Colocar role="button" numa <div> só muda o anúncio no leitor; ela continua sem foco e sem clique por Enter/Espaço.
2. aria-hidden="true" em elemento focável: cria um foco fantasma — o teclado para lá, mas o leitor fica mudo!
3. Armadilha de teclado (Keyboard Trap): o usuário entra num modal com Tab e não consegue sair nem fechar com Esc.
RESUMO

O que você precisa levar deste capítulo

“HTML semântico primeiro; ARIA só onde o HTML não alcança.” Semântica nativa + ordem de foco limpa + feedback em regiões vivas.
  • Use marcos semânticos: <header>, <nav>, <main>, <aside>, <footer>.
  • 1ª Regra da ARIA: prefira <button> e <a href> nativos.
  • aria-label / labelledby nomeiam; aria-live anuncia atualizações dinâmicas.
  • tabindex="0" (ordem natural), -1 (foco via JS), nunca > 0.
TESTE RÁPIDO

4 questões no estilo FGV

1. O que acontece se um botão só com ícone de lupa não tiver texto nem aria-label?

O leitor de tela anuncia apenas "botão" (sem dizer o que ele faz). Com aria-label="Buscar", o leitor anuncia "Buscar, botão".

2. Qual a diferença entre aria-live="polite" e aria-live="assertive"?

polite aguarda o leitor terminar o que está lendo antes de anunciar; assertive interrompe imediatamente.

3. Por que tabindex="1", tabindex="2" é considerado má prática?

Porque cria uma ordem artificial prioritária que quebra a sequência lógica do DOM e confunde usuários de teclado.

4. Quando usar aria-hidden="true"?

Apenas em elementos puramente decorativos e não focáveis (como um ícone ao lado de um texto que já explica a ação).
