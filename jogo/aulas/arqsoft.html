CONCEITO

GoF: a “Gangue dos Quatro” e seus 23 padrões

Livro Design Patterns (1994), de Gamma, Helm, Johnson e Vlissides. Padrão = solução reutilizável para um problema recorrente de projeto, com nome, problema, solução e consequências.

PropósitoQtdePergunta que respondeMembros
Criacional5Como o objeto nasce?Abstract Factory, Builder, Factory Method, Prototype, Singleton
Estrutural7Como as peças se encaixam?Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
Comportamental11Quem faz o quê e como conversam?Chain of Resp., Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor
O GoF classifica por propósito (criacional, estrutural, comportamental) e por escopo: de classe (relações por herança, fixas em compilação — ex.: Factory Method, Template Method) ou de objeto (composição, mutáveis em execução — a maioria).
O PROBLEMA

Por que não usar new em todo lugar?

Cliente amarrado à classe concreta
class Aviso {
  void avisar(String t) {
    Email m = new Email(); // preso ao e-mail
    m.enviar(t);
  }
}

Amanhã vem SMS e WhatsApp: você abre e altera a classe Aviso a cada canal novo.

Cliente depende de abstração
class Aviso {
  private final Mensageiro m;
  Aviso(Mensageiro m) { this.m = m; }
  void avisar(String t) { m.enviar(t); }
}

Quem cria o objeto concreto fica em outro lugar (uma fábrica). Aviso fica fechado para modificação.

Pergunta mágica: “Quem decide qual classe será instanciada?”Se a resposta for “alguém diferente do cliente”, há um padrão criacional por perto.
FACTORY METHOD

Factory Method: a subclasse escolhe o produto

// Criador: usa o produto, não sabe qual
abstract class Notificador {
  abstract Mensagem criarMensagem();
  void enviar(String txt) {
    Mensagem m = criarMensagem();
    m.despachar(txt);
  }
}
class NotificadorEmail extends Notificador {
  Mensagem criarMensagem() {
    return new Email();
  }
}
Factory Method define uma interface para criar um objeto, mas deixa as subclasses decidirem qual classe instanciar (escopo de classe, via herança).
ABSTRACT FACTORY

Abstract Factory: uma fábrica de famílias

🛋️
Loja de móveis com coleções “Clássica” e “Moderna”: se você escolhe a coleção, cadeira, mesa e sofá vêm combinando. Ninguém mistura sofá clássico com mesa moderna por engano.
interface TemaFactory {
  Botao criarBotao();
  Janela criarJanela();
}
class TemaEscuroFactory implements TemaFactory {
  public Botao criarBotao()   { return new BotaoEscuro(); }
  public Janela criarJanela() { return new JanelaEscura(); }
}
// cliente recebe a fábrica e nunca dá new
Tela(TemaFactory f) {
  botao = f.criarBotao(); janela = f.criarJanela();
}
Abstract Factory fornece uma interface para criar famílias de objetos relacionados ou dependentes sem especificar suas classes concretas.
BUILDER

Builder: montar passo a passo

Problema: um objeto com muitos campos opcionais gera “construtores telescópicos” — new Processo(n, null, null, true, false, null). Quem lê não sabe o que é cada null.

class Processo {
  private final String numero, classe; private final boolean segredo;
  private Processo(Builder b) { numero = b.numero; classe = b.classe; segredo = b.segredo; }

  static class Builder {
    private final String numero; private String classe; private boolean segredo;
    Builder(String numero)        { this.numero = numero; }
    Builder classe(String c)      { this.classe = c; return this; }
    Builder segredo(boolean s)    { this.segredo = s; return this; }
    Processo build()              { return new Processo(this); }
  }
}
Processo p = new Processo.Builder("0801234-56.2026.8.15.0001")
                 .classe("Procedimento Comum").segredo(true).build();
Builder separa a construção de um objeto complexo da sua representação, de modo que o mesmo processo de construção possa criar representações diferentes. No GoF original há ainda um Diretor que comanda os passos; a versão “fluente” acima é a variante popular em Java.
PROTOTYPE

Prototype: criar copiando

📄
Em vez de redigir do zero cada mandado, o cartório tem um modelo pronto e tira cópias, mudando só nome e data.
class Modelo implements Cloneable {
  String titulo; List<String> clausulas;
  @Override public Modelo clone() {
    try {
      Modelo c = (Modelo) super.clone();
      c.clausulas = new ArrayList<>(clausulas); // cópia profunda
      return c;
    } catch (CloneNotSupportedException e) {
      throw new AssertionError(e);
    }
  }
}
Quando usar: criar do zero é caro (consulta, cálculo) ou as classes só são conhecidas em execução.
Cuidado: Object.clone() faz cópia rasa: a lista seria compartilhada entre original e clone. Por isso copiamos a lista à mão.
Prototype especifica os tipos de objetos a criar usando uma instância protótipo e cria novos objetos copiando esse protótipo.
SINGLETON

Singleton: só existe um

public final class Config {
  // criado na carga da classe: thread-safe
  private static final Config INSTANCIA = new Config();
  private Config() {}           // ninguém dá new
  public static Config getInstance() {
    return INSTANCIA;
  }
}
// Alternativa recomendada por Joshua Bloch:
public enum Registro { INSTANCIA; }
construtor privado+campo estático+acesso global
Críticas: é estado global disfarçado, esconde dependências, atrapalha testes (difícil trocar por mock) e, na versão “preguiçosa” sem sincronização, duas threads podem criar duas instâncias.
Singleton garante que uma classe tenha uma única instância e fornece um ponto global de acesso a ela.

RESUMO

Resumo do capítulo

GoF = 23 padrões: 5 criacionais · 7 estruturais · 11 comportamentais.Criacionais: ABFPS — Abstract Factory, Builder, Factory Method, Prototype, Singleton.
  • Criacionais escondem qual classe é instanciada e como.
  • Factory Method: subclasse decide (escopo de classe).
  • Abstract Factory: famílias de produtos compatíveis.
  • Builder: construção em etapas; evita construtor telescópico.
  • Prototype: clona; atenção à cópia rasa × profunda.
  • Singleton: instância única + acesso global; cuidado com threads e testes.
TESTE RÁPIDO

Teste rápido (estilo FGV)

1) Um framework de documentos define abstract Documento criar() e cada aplicação concreta sobrescreve esse método. Qual padrão?

Factory Method A criação é delegada às subclasses via herança. Não é Abstract Factory, que cria famílias de produtos.

2) Um sistema precisa gerar componentes visuais compatíveis para os temas claro e escuro sem que o cliente conheça as classes concretas. Qual padrão?

Abstract Factory “Família de objetos relacionados” é a pista.

3) “O Builder é indicado quando é preciso garantir que uma classe tenha uma única instância.” Certo ou errado?

Errado Isso é Singleton. Builder serve para montar objetos complexos em etapas.

4) Por que super.clone() pode causar bug no Prototype quando o objeto tem uma lista?

Cópia rasa A referência da lista é copiada, então original e clone passam a compartilhar a mesma lista. É preciso copiar profundamente.

🔌
Analogia do dia: estrutural é como ligar aparelhos (adaptador de tomada, filtro de linha, extensão). Comportamental é como combinar quem faz o quê numa equipe (quem avisa quem, quem decide a estratégia).
ADAPTER

Adapter: o adaptador de tomada

interface Pagamento { void pagar(BigDecimal v); }

class GatewayAdapter implements Pagamento {
  private final GatewayAntigo antigo;  // adaptado
  GatewayAdapter(GatewayAntigo a) { antigo = a; }
  public void pagar(BigDecimal v) {
    antigo.makePayment(v.doubleValue());
  }
}
Adapter converte a interface de uma classe em outra interface que o cliente espera, permitindo que classes incompatíveis trabalhem juntas. Há versão de objeto (composição, acima) e de classe (herança múltipla).
DECORATOR

Decorator: embrulhos que somam poderes

🎁
Um presente dentro de outra caixa, dentro de outra… Por fora é sempre “uma caixa” (mesma interface), mas cada camada acrescenta algo.
InputStream in = new BufferedInputStream(
                   new GZIPInputStream(
                     new FileInputStream("autos.gz")));

class LogDecorator implements Notificador {
  private final Notificador interno;
  LogDecorator(Notificador n) { interno = n; }
  public void enviar(String m) {
    log.info(m);           // extra
    interno.enviar(m);     // delega
  }
}
Decorator anexa responsabilidades adicionais a um objeto dinamicamente, mantendo a mesma interface: alternativa flexível à herança para estender funcionalidade.
PROXY

Proxy: o porteiro do objeto

class ImagemProxy implements Imagem {
  private final String arquivo;
  private ImagemReal real;          // ainda não existe
  ImagemProxy(String a) { arquivo = a; }
  public void exibir() {
    if (real == null) real = new ImagemReal(arquivo);
    real.exibir();
  }
}

Tipos de proxy:

  • Virtual: adia criação cara (lazy loading — o Hibernate usa proxies assim).
  • Remoto: representa objeto em outro processo/máquina.
  • Proteção: confere permissão antes de repassar.
  • Inteligente/cache: conta referências, guarda resultados.
Proxy fornece um substituto (representante) de outro objeto para controlar o acesso a ele, com a mesma interface do objeto real.

Quem altera interface é o Adapter. O Decorator preserva a interface e soma responsabilidades.
FACADE · COMPOSITE

Facade simplifica; Composite monta árvores

class CertidaoFacade {       // 1 chamada simples
  byte[] emitir(String cpf) {
    var p = pessoas.buscar(cpf);
    var r = distribuidor.consultar(p);
    var pdf = gerador.gerar(r);
    return assinador.assinar(pdf);
  }
}

Facade: interface unificada e de alto nível para um subsistema; o cliente não precisa conhecer 4 classes.

interface Item { long tamanho(); }
class Pasta implements Item {
  List<Item> filhos = new ArrayList<>();
  public long tamanho() {
    return filhos.stream().mapToLong(Item::tamanho).sum();
  }
}
Composite compõe objetos em estruturas de árvore (parte-todo) e permite tratar objetos individuais e composições de maneira uniforme. Completam os estruturais: Bridge (separa abstração da implementação) e Flyweight (compartilha estado intrínseco de muitos objetos).

STRATEGY

Strategy: trocar o algoritmo como quem troca de rota

interface Frete { BigDecimal calcular(Pedido p); }
class Sedex implements Frete { ... }

class Checkout {
  private Frete frete;                  // composição
  void setFrete(Frete f) { frete = f; }
  BigDecimal total(Pedido p) {
    return p.valor().add(frete.calcular(p));
  }
}
checkout.setFrete(p -> BigDecimal.ZERO); // lambda!
Strategy define uma família de algoritmos, encapsula cada um e os torna intercambiáveis; o algoritmo varia independentemente dos clientes que o usam.
OBSERVER

Observer: “me avise quando mudar”

🔔
Você clica no “sininho” de um canal: quando sai vídeo novo, todos os inscritos são avisados. O canal não sabe quem você é, só que você está na lista.
interface Observador { void atualizar(Movimento m); }

class Processo {
  private final List<Observador> obs = new ArrayList<>();
  void inscrever(Observador o) { obs.add(o); }
  void movimentar(Movimento m) {
    historico.add(m);
    obs.forEach(o -> o.atualizar(m));
  }
}
Observer define uma dependência um-para-muitos: quando um objeto muda de estado, todos os seus dependentes são notificados e atualizados automaticamente. É a semente do publish/subscribe.
PEGADINHA

Strategy × Template Method × State

abstract class Importador {
  // template method: esqueleto FINAL
  public final void importar() {
    ler(); validar(); salvar();
  }
  protected abstract void ler();
  protected abstract void validar();
  protected void salvar() { repo.salvar(dados); } // gancho
}
PadrãoMecanismoQuem troca?
Template Methodherançasubclasse, em compilação
Strategycomposiçãoo cliente escolhe
Statecomposiçãoo próprio objeto, ao mudar de estado
“No Template Method, o cliente injeta o algoritmo em tempo de execução por composição.”
Isso descreve Strategy. Template Method usa herança: a superclasse fixa a ordem dos passos (princípio de Hollywood) e as subclasses preenchem.
“Command e Memento são estruturais.”
Ambos são comportamentais — e juntos implementam o “desfazer”.
RESUMO

Resumo do capítulo

Adapter MUDA a interface; Decorator e Proxy MANTÊM.Decorator acrescenta, Proxy controla. Strategy = composição escolhida pelo cliente; Template Method = herança com esqueleto fixo.
  • Estruturais (7): Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.
  • Facade = porta simples para subsistema; Composite = árvore parte-todo uniforme.
  • Comportamentais (11): Chain, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor.
  • Observer = 1 para N com notificação automática.
  • Command = pedido como objeto (fila, log, desfazer).
TESTE RÁPIDO

Teste rápido (estilo FGV)

1) Uma biblioteca de terceiros expõe makePayment(double), mas o sistema espera pagar(BigDecimal). Qual padrão resolve?

Adapter Converte uma interface na outra esperada pelo cliente.

2) Um editor precisa de “desfazer” para cada ação do usuário, guardando as ações numa pilha. Qual padrão representa as ações?

Command Cada ação vira objeto com executar() e desfazer(). (Memento pode guardar o estado, mas a ação em si é Command.)

3) “O Facade impede o acesso direto às classes do subsistema.” Certo ou errado?

Errado O Facade oferece um atalho simples, mas não proíbe quem precisar de usar as classes internas.

4) Um pedido muda de comportamento conforme esteja “aberto”, “pago” ou “enviado”, cada um em uma classe. Strategy ou State?

State A troca é feita pelo próprio objeto conforme seu estado interno, não escolhida pelo cliente.

IoC

Inversão de controle: “não nos chame, nós chamamos você”

Exemplos de IoC: o servlet container chama seu doGet(); o Spring cria seus beans e chama seus @Controller; o JUnit chama seus métodos @Test; o Template Method chama os passos da subclasse.

Inversão de Controle (IoC) é o princípio em que o fluxo de controle (ou a criação de objetos) é transferido do código da aplicação para um framework/contêiner. Injeção de dependência é uma das formas de realizar IoC.
INJEÇÃO DE DEPENDÊNCIA

DI: receber em vez de fabricar

Acoplado: a classe dá new
class RelatorioService {
  private final RepoMySql repo =
      new RepoMySql();
  // teste? precisa de MySQL real
}
Injetado pelo construtor
@Service
class RelatorioService {
  private final Repositorio repo;
  RelatorioService(Repositorio repo) {
    this.repo = repo;
  }
}
Contêiner lê config / anotações→cria RepoJpa→cria RelatorioService(repoJpa)→no teste: new RelatorioService(mock)
No Spring (desde a 4.3), se a classe tem um único construtor, ele é usado para injeção mesmo sem @Autowired.
TIPOS

Três formas de injetar (e um primo)

FormaComoQuando
Construtorparâmetros do construtordependências obrigatórias; permite campos final e objeto sempre válido — a preferida
SettersetRepo(...)dependências opcionais ou trocáveis depois
Interfacea classe implementa um método injetar(...) definido por interfacerara hoje (classificação de Martin Fowler)
Campo (@Autowired no atributo)reflexão no campo privadofunciona, mas esconde dependências e dificulta testes sem o contêiner
Service Locator não é DI: a classe pede a dependência a um registro (Locator.get(Repo.class)). Também desacopla da implementação, mas a classe passa a depender do localizador e a dependência fica escondida.
PEGADINHA

IoC × DI × DIP: três siglas, três coisas

“Injeção de dependência e Princípio da Inversão de Dependência são sinônimos.”
DIP (o “D” do SOLID) diz o que fazer: módulos de alto e baixo nível dependem de abstrações. DI é uma técnica que ajuda a cumprir o DIP. Dá para usar DI injetando classe concreta (sem cumprir DIP).
SOA

SOA: o sistema como um conjunto de serviços com contrato

Princípios clássicos de serviço: contrato padronizado, baixo acoplamento, abstração, reusabilidade, autonomia, ausência de estado, descoberta e composição.

SOA (arquitetura orientada a serviços) organiza a TI como serviços de negócio reutilizáveis, de baixo acoplamento, expostos por contratos e consumidos de forma interoperável. Pode ser implementada com SOAP ou REST; o ESB é comum, mas não obrigatório.

MICROSSERVIÇOS

Monólito × microsserviços

Ganhos: deploy e escala independentes, times autônomos, tecnologia por serviço, falha isolada. Custos: rede (latência, falhas parciais), consistência eventual, observabilidade e operação mais difíceis.

Microsserviços: aplicação composta por serviços pequenos e autônomos, cada um rodando em processo próprio, organizados em torno de capacidades de negócio, com implantação independente e dados próprios (database per service), comunicando-se por mecanismos leves (HTTP/REST, gRPC, mensageria).

TESTE RÁPIDO

Teste rápido (estilo FGV)

1) Uma classe obtém seu repositório chamando Contexto.buscar("repo"). Isso é injeção de dependência?

Não É Service Locator: a própria classe busca a dependência. Na DI ela é entregue de fora.

2) Qual forma de injeção garante que o objeto nunca exista sem suas dependências obrigatórias?

Construtor Sem os argumentos, o objeto nem é criado; os campos podem ser final.

3) “Em microsserviços, recomenda-se um banco de dados compartilhado por todos os serviços para garantir consistência.” Certo ou errado?

Errado O padrão é banco por serviço; banco compartilhado acopla os serviços. Consistência entre serviços costuma ser eventual (sagas).

4) PUT é idempotente? E POST?

PUT: sim repetir deixa o recurso no mesmo estado. POST: não repetir pode criar dois recursos.

EDA

Comando × evento e o publish/subscribe

Comando: pedido no imperativo, tem destinatário, pode ser recusado.
EmitirIntimacao
Evento: fato que já aconteceu, no passado, imutável, sem destinatário certo.
SentencaPublicada
Na arquitetura orientada a eventos, componentes se comunicam pela produção e consumo assíncronos de eventos por meio de um intermediário (broker), gerando baixo acoplamento temporal e espacial. Custo: consistência eventual e depuração mais difícil.
KAFKA

Kafka: um caderno onde só se escreve no fim

  • Log distribuído e append-only; mensagem fica guardada pelo período de retenção (não some ao ser lida).
  • Cada consumidor guarda seu offset (posição); pode reprocessar desde o início.
  • Ordem garantida só dentro da partição; mesma chave → mesma partição.
  • Num consumer group, cada partição é lida por um só consumidor do grupo; grupos diferentes recebem tudo.
RABBITMQ

RabbitMQ: o carteiro que entrega e esquece

ExchangeEntrega para…
directfilas cuja binding key é igual à routing key
fanouttodas as filas ligadas (ignora a chave)
topicpadrões com * (exatamente uma palavra) e # (zero ou mais), ex.: tjpb.*.sentenca
headersconforme atributos do cabeçalho

Protocolo principal: AMQP 0-9-1. Após o ack do consumidor, a mensagem sai da fila.

É justamente o contrário: at-least-once pode repetir; o consumidor deve ser idempotente (ex.: guardar o ID dos eventos já processados).
PADRÕES DE EVENTOS

Event Sourcing, CQRS, Saga e Outbox

PadrãoIdeia
Event Sourcingguarda a sequência de eventos, não só o estado final; o estado é reconstruído reaplicando-os (extrato bancário → saldo)
CQRSsepara o modelo de escrita (comandos) do de leitura (consultas), que podem até ter bancos diferentes
Sagatransação longa entre serviços como sequência de transações locais, com ações compensatórias se algo falhar; por coreografia (eventos) ou orquestração (coordenador)
Transactional Outboxgrava o evento numa tabela “outbox” na mesma transação do dado; um relay publica depois — evita salvar sem publicar
Reservar vaga ✓→Cobrar ✗→compensa: cancelar reserva
CQRS e Event Sourcing combinam bem, mas são independentes: dá para usar um sem o outro.
CLEAN ARCHITECTURE

Clean Architecture: tudo aponta para o centro

  1. Entidades: regras de negócio da empresa.
  2. Casos de uso: regras da aplicação (“arquivar processo”).
  3. Adaptadores de interface: controllers, presenters, gateways/repositórios.
  4. Frameworks e drivers: Spring, banco, web, UI.
Banco e framework são detalhes: dá para testar os casos de uso sem eles.
Regra da Dependência (Robert C. Martin): dependências de código-fonte só podem apontar para dentro. Nada de um círculo interno pode conhecer nomes (classes, funções, variáveis) de um círculo externo.
NA PRÁTICA

Como o núcleo usa o banco sem conhecê-lo? Portas!

// NÚCLEO (caso de uso) — nenhum import de JPA ou Spring
public interface ProcessoRepository {          // porta (definida DENTRO)
  Optional<Processo> porNumero(String numero);
  void salvar(Processo p);
}
public class ArquivarProcesso {
  private final ProcessoRepository repo;
  public ArquivarProcesso(ProcessoRepository repo) { this.repo = repo; }
  public void executar(String numero) {
    Processo p = repo.porNumero(numero).orElseThrow();
    p.arquivar();                                    // regra na entidade
    repo.salvar(p);
  }
}
// CAMADA EXTERNA (adaptador) — depende do núcleo, nunca o contrário
class ProcessoRepositoryJpa implements ProcessoRepository { ... }
É o DIP aplicado à arquitetura. A mesma ideia aparece na Arquitetura Hexagonal (Alistair Cockburn: portas e adaptadores) e na Onion Architecture (Jeffrey Palermo).
DDD ESTRATÉGICO

DDD: falar a língua do negócio, dentro de fronteiras

  • Linguagem ubíqua: os mesmos termos na fala do especialista e no código.
  • Bounded context: fronteira explícita dentro da qual um modelo (e seus termos) é consistente.
  • Mapa de contextos: relações como Shared Kernel, Customer/Supplier, Conformist, Anticorruption Layer (ACL), Open Host Service, Published Language, Separate Ways.
DDD (Eric Evans, 2003) foca o software no domínio e em sua lógica, construindo um modelo em colaboração com os especialistas. O design estratégico trata de contextos e suas relações; o tático, dos blocos de construção do modelo.

// Objeto de Valor com record (Java 16+)
public record Dinheiro(BigDecimal valor,
                      String moeda) {
  public Dinheiro {                // valida
    if (valor.signum() < 0)
      throw new IllegalArgumentException();
  }
  Dinheiro somar(Dinheiro o) {     // novo objeto
    return new Dinheiro(valor.add(o.valor()), moeda);
  }
}
“Cada entidade do agregado deve ter seu próprio repositório e pode ser referenciada diretamente por outros agregados.”
Repositório existe para a raiz do agregado; de fora, só se referencia a raiz (de preferência pelo ID). E o modelo anêmico (entidade só com getters/setters, regras em serviços) é antipadrão no DDD.

Não, pela regra A entidade é o círculo mais interno e não deve conhecer frameworks (círculo externo).

🩺
Analogia do dia: métricas são os sinais vitais do software. Febre (defeitos), pressão (complexidade), tempo de recuperação depois de uma gripe (MTTR). Um número só não dá diagnóstico; o conjunto, sim.
COBERTURA

Cobertura: quanto do código os testes “pisaram”

int desconto(int idade, boolean servidor) {
  int d = 0;
  if (idade >= 60) d += 10;
  if (servidor)    d += 5;
  return d;
}
// Teste único: desconto(70, true) == 15
CritérioCom 1 teste (70, true)
Comandos / linhas100% — todas as linhas rodaram
Decisões (branches)50% — os lados falsos dos dois if nunca rodaram
Caminhos1 de 4 (V/V, V/F, F/V, F/F)

Acrescentando desconto(20, false) == 0, a cobertura de decisões chega a 100% com 2 testes; a de caminhos ainda exigiria 4.

Cobertura de código = percentual de elementos (comandos, decisões, condições, caminhos) executados pelos testes. Hierarquia: 100% de decisões implica 100% de comandos, mas não o inverso.
PEGADINHA

Cobertura alta = testes bons?

Teste que “cobre” e não verifica nada
@Test void testaDesconto() {
  desconto(70, true);   // sem assert!
}

Cobertura de linhas: 100%. Bugs encontrados: zero.

Teste de mutação dá a resposta

A ferramenta (ex.: PIT, em Java) cria mutantes: troca >= por >, += por -=… Se algum teste falha, o mutante foi morto.

escore de mutação = mutantes mortos ÷ mutantes (não equivalentes)

Para matar o mutante idade > 60, é preciso testar a fronteira idade = 60.

“100% de cobertura de comandos garante a ausência de defeitos.”
Cobertura mostra o que não foi testado; não prova que o testado está certo. Testes mostram a presença de defeitos, não sua ausência.
DEFEITOS

Densidade de defeitos e outras métricas de produto

densidade de defeitos = nº de defeitos ÷ tamanho
ex.: 18 defeitos em 12 KLOC → 18 ÷ 12 = 1,5 defeito/KLOC

O tamanho pode ser KLOC (mil linhas) ou pontos de função — este último compara linguagens diferentes de forma mais justa.

MétricaO que indica
Defeitos escapadosbugs achados em produção em vez de nos testes
Duplicação% de código repetido (manutenção mais cara)
Acoplamento / coesãométricas CK: CBO (acoplamento entre objetos), LCOM (falta de coesão), DIT (profundidade de herança), NOC (nº de filhos), WMC, RFC
Dívida técnicaesforço estimado para corrigir problemas de manutenibilidade
Ferramentas como o SonarQube reúnem essas métricas e aplicam um quality gate (porta de qualidade): se o código novo não atinge as condições (cobertura mínima, sem bugs graves…), o pipeline reprova. Os limites exatos dependem da configuração.
COMPLEXIDADE

Complexidade ciclomática (McCabe)

Grafo da função desconto: N = 6 nós, E = 7 arestas, P = 1 componente.

M = E − N + 2P
M = 7 − 6 + 2 = 3
atalho: decisões + 1 = 2 + 1 = 3

M = nº de caminhos linearmente independentes → mínimo de casos de teste do teste de caminho básico. Note: 3 ≠ 4 caminhos completos.

Complexidade ciclomática mede a complexidade estrutural pelo grafo de fluxo de controle: V(G) = E − N + 2P. Valores altos indicam código difícil de testar e manter.
MTTR · MTBF

Quanto tempo fica de pé? Quanto tempo leva para voltar?

MTTR = tempo total de reparo ÷ nº de incidentes = (20+40+60) ÷ 3 = 40 min
MTBF = tempo em operação ÷ nº de falhas = (720 h − 2 h) ÷ 3 ≈ 239,3 h
Disponibilidade = MTBF ÷ (MTBF + MTTR) = 239,3 ÷ (239,3 + 0,67) ≈ 99,72%
Confere: 718 h no ar ÷ 720 h = 99,72%. Para aumentar a disponibilidade: falhar menos (↑MTBF) ou voltar mais rápido (↓MTTR).
MTTR (Mean Time To Repair/Recovery/Restore) é o tempo médio para restabelecer o serviço após uma falha. O “R” varia conforme a fonte (reparo, recuperação, resolução); leia como o enunciado define.
DORA

As 4 métricas-chave de entrega (DORA)

Programa DORA (DevOps Research and Assessment), base do livro Accelerate e do relatório anual State of DevOps. Nos relatórios, os times de melhor desempenho fazem deploy sob demanda (várias vezes ao dia) e restauram em menos de uma hora. As faixas e até os nomes de métricas mudam entre edições (relatórios recentes chamam a restauração de failed deployment recovery time) — confira o relatório oficial.

Achado central do DORA: velocidade e estabilidade não são opostas; os melhores times são bons nas duas ao mesmo tempo.

Calculando as 4 chaves de um mês

Dado do mêsMétricaResultado

commits levaram, em média, 6 h até produçãoLead time de mudanças6 horas
4 dos 40 deploys geraram incidente ou rollbackTaxa de falha de mudança4 ÷ 40 = 10%

“Lead time de mudanças é o tempo desde a abertura do pedido pelo cliente até a entrega.”
No DORA, é do commit (código pronto) até estar em produção. O tempo desde o pedido do cliente é o lead time do fluxo/Kanban, mais amplo.
“Para reduzir a taxa de falha, o ideal é fazer deploys grandes e raros.”
Lotes pequenos e frequentes reduzem risco e facilitam restaurar — por isso CI/CD, feature flags e testes automatizados melhoram as quatro.

RESUMO

Resumo do capítulo

MTTR = reparo total ÷ nº de incidentes. Decisão 100% ⇒ comando 100%, nunca o contrário.DORA: 2 de velocidade (frequência de deploy, lead time) + 2 de estabilidade (taxa de falha, tempo para restaurar).
  • Cobertura mostra o que falta testar; mutação mostra se os testes verificam.
  • Densidade de defeitos = defeitos ÷ KLOC (ou pontos de função).
  • Ciclomática: E − N + 2P = decisões + 1 = mínimo de caminhos independentes.
  • Disponibilidade = MTBF ÷ (MTBF + MTTR).
  • Velocidade e estabilidade andam juntas; métricas não devem virar meta isolada.
TESTE RÁPIDO

Teste rápido (estilo FGV)

1) Em um mês houve 5 incidentes que somaram 150 minutos de indisponibilidade. Qual o MTTR?

30 min 150 ÷ 5. Cuidado para não responder 150 (total) nem dividir ao contrário.

2) Um método tem um if e um while, sem outras decisões. Complexidade ciclomática?

3 Cada if/while conta como decisão: 2 + 1 = 3.

3) “Atingir 100% de cobertura de comandos garante 100% de cobertura de decisões.” Certo ou errado?

Errado É o inverso: decisões ⇒ comandos. Um if sem else executado só no lado verdadeiro já cobre todas as linhas.

4) Frequência de deploy e lead time de mudanças medem velocidade ou estabilidade?

Velocidade As de estabilidade são taxa de falha de mudança e tempo para restaurar o serviço.
