📖
Analogia do dia: o Git é um álbum de fotos do código. Antes de colar a foto no álbum (commit), você escolhe quais fotos vão para a mesa de seleção (staging). Branches são rascunhos paralelos para testar ideias sem estragar o álbum principal.
FUNDAMENTOS

As 3 áreas do Git (e o remoto)

Branch no Git não é cópia pesada de pasta: é apenas um ponteiro leve e móvel para um commit. HEAD aponta para a branch (ou commit) atual.
INTEGRAÇÃO

Merge (Fast-Forward × 3-Way)

Conflito acontece quando duas branches alteram a mesma região do mesmo arquivo: o Git pausa o merge e pede escolha humana.

HISTÓRICO

Merge × Rebase

git merge

Junta duas pontas criando um commit de merge (ou fast-forward).

Preserva a história real e os hashes originais.

Seguro em branches compartilhadas.

git rebase

Pega seus commits e os reaplica no topo da outra branch.

Gera histórico linear e limpo.

Cria novos hashes (reescreve histórico).

✗ Fazer git rebase na branch main já enviada ao remoto. ✓ Regra de ouro: nunca dê rebase em branch pública/compartilhada — só na sua branch local antes de abrir PR/MR.
FLUXO CLÁSSICO

Gitflow: organizado por papéis de branch

Gitflow mantém duas branches perpétuas (main e develop) e branches de apoio (feature, release, hotfix). É indicado para software com versões planejadas, mas gera atrito se a equipe quer publicar várias vezes por dia.
FLUXO ÁGIL

Trunk-Based Development (TBD)

🚂
Analogia: em vez de cada passageiro montar um trem separado por semanas (Gitflow), todos embarcam no mesmo trem expresso (main/trunk) com pacotes pequenos todo dia.
CritérioGitflowTrunk-Based (TBD)
Branches longasmain + develop + releaseApenas a main (trunk)
Branches de featurePodem durar semanasCurtíssimas (horas ou 1–2 dias)
Código inacabadoFica isolado na branchVai pra main atrás de feature flag
Ideal paraReleases agendadas / móveisCI/CD rápido e deploy contínuo
OPERAÇÃO DECLARATIVA

GitOps: o Git manda no cluster

No GitOps, tanto o código quanto os manifestos de infraestrutura/Kubernetes moram no Git. Toda mudança entra via Pull Request revisado.

Push tradicional

Git→CI→empurra p/ Cluster

A esteira precisa de credencial admin do cluster e não vê se alguém mexeu à mão lá dentro.

Pull GitOps (ArgoCD / Flux)

Git←Agente no Cluster

O agente compara o estado real com o Git e reconcilia qualquer desvio (drift) sozinho.

Pilares do GitOps: estado declarativo, versionado e imutável no Git, puxado automaticamente por agentes e reconciliado continuamente.
PEGADINHA

Onde a FGV tenta te derrubar em Git

✗ “git pull apenas baixa as referências remotas sem alterar os arquivos locais.” ✓ Quem só baixa sem integrar é git fetch. git pull faz fetch + merge (ou rebase).
✗ “Gitflow é obrigatório para usar CI/CD moderno.” ✓ Pelo contrário: o Trunk-Based Development é a prática recomendada para CI/CD de alta frequência, usando feature flags.
✗ “GitOps significa apenas guardar scripts bash no Git.” ✓ GitOps exige estado declarativo + reconciliação automática por agente (modelo pull).
RESUMO

Capítulo 1 numa colinha

Merge preserva história; Rebase lineariza. TBD acelera; GitOps reconcilia.Working Tree → (add) → Staging → (commit) → Repo Local → (push) → Remoto.
  • fetch baixa sem mesclar; pull baixa e mescla.
  • Fast-forward não cria commit extra; 3-way cria commit de merge com 2 pais.
  • Nunca dê rebase em branch compartilhada (altera os hashes).
  • Gitflow: main + develop + feature/release/hotfix.
  • Trunk-Based: integração contínua na main com feature flags.
  • GitOps: Git é fonte única da verdade; agente pull detecta e corrige drift.
TESTE RÁPIDO

Pense antes de abrir

1) Qual comando baixa commits do remoto sem alterar a branch em que você está trabalhando?

git fetch Ele atualiza as referências remotas localmente, sem fazer merge automático (ao contrário do git pull).

2) Em um hotfix urgente no Gitflow, a partir de qual branch ele nasce e para quais ele volta?

Nasce da main; volta para main e develop Assim a correção vai para produção e também não se perde no próximo release.

3) Como o Trunk-Based Development evita que uma feature inacabada quebre o usuário em produção?

Feature flags (toggles) O código é integrado na main diariamente, mas fica desligado em produção até estar pronto.

4) No GitOps com ArgoCD, o que acontece se um operador editar um Deployment direto com kubectl?

Detecção de drift e reconciliação O agente percebe que o cluster divergiu do Git e restaura o estado declarado.

🏭
Analogia do dia: uma esteira de fábrica de bolos. A cada receita alterada, um robô mistura, assa e prova o bolo (CI). Se deixa o bolo embalado esperando o gerente dizer "vai pra vitrine", é Delivery. Se o robô já põe na vitrine sozinho, é Deployment.
CONCEITO CENTRAL

CI vs Continuous Delivery vs Continuous Deployment

CI automatiza integração, build e testes a cada mudança. Continuous Delivery garante que o software está sempre pronto para ir à produção com um clique manual. Continuous Deployment publica automaticamente toda mudança aprovada nos testes.

PIPELINE AS CODE

Por que o pipeline mora no repositório?

📜
Analogia: antes, alguém clicava em 40 telas no Jenkins para configurar um build (se o servidor morresse, perdia tudo). Hoje, a receita do build é um arquivo de texto junto do código.
  • Versionado: se o código da v2 precisa de Java 21 e a v1 de Java 17, cada branch tem seu próprio pipeline.
  • Auditável: mudanças na esteira passam por Code Review no Pull Request.
  • Reprodutível: fácil de recriar em outro servidor ou runner.
Pipeline as Code trata a definição da esteira de CI/CD como código-fonte versionado no mesmo repositório da aplicação.

DEPLOY SEGURO · PARTE 2

Canary Release (Canário)

Inspirado no canário da mina de carvão: se os 5% apresentarem erro ou lentidão nas métricas, você corta o Canary antes de afetar os outros 95%. Se tudo for bem, sobe para 25%, 50%, 100%.

PEGADINHA

Pegadinhas clássicas de CI/CD

✗ “CI já coloca o código em produção.” ✓ CI vai até build e testes automatizados; quem coloca em produção é o CD (Delivery/Deployment).
✗ “Blue-Green divide 10% do tráfego para a versão nova enquanto 90% ficam na antiga.” ✓ Dividir tráfego em porcentagem pequena é Canary. Blue-Green vira 100% do tráfego entre dois ambientes completos.
✗ “Artifact e Cache são a mesma coisa no GitLab CI / GitHub Actions.” ✓ Cache acelera builds futuros (dependências); Artifact passa resultados do build atual entre estágios.
RESUMO

Capítulo 2 numa colinha

CI = testa; Delivery = pronto com botão; Deployment = automático.Jenkins (Jenkinsfile), GitLab CI (.gitlab-ci.yml), GitHub Actions (workflows/*.yml).
  • Pipeline as Code versiona a esteira junto com o código da aplicação.
  • Stages organizam fases; jobs dentro do mesmo stage podem rodar em paralelo.
  • Rolling Update troca instâncias aos poucos (convivem v1 e v2).
  • Blue-Green usa dois ambientes completos e dá rollback instantâneo.
  • Canary libera para pequena fatia de usuários e monitora antes de expandir.
TESTE RÁPIDO

Pense antes de abrir

1) Uma empresa automatizou build, testes e deploy em homologação, mas exige clique de um gerente para subir em produção. Isso é:

Continuous Delivery O código está sempre pronto para produção, mas a liberação final tem aprovação manual.

2) Qual estratégia de deploy reduz o raio de impacto testando a v2 com apenas 2% dos usuários reais?

Canary Release Permite validar métricas reais com risco mínimo antes de escalar para 100%.

3) Qual arquivo define o pipeline declarativo ou scripted no Jenkins?

Jenkinsfile Versionado na raiz do repositório (Pipeline as Code).

4) Qual a principal desvantagem do Blue-Green Deployment frente ao Rolling Update?

Custo de infraestrutura Exige manter dois ambientes de produção completos simultaneamente durante a transição.

CAPÍTULO 3

Docker e containers

🐳
1. Container × VMKernel compartilhado, namespaces e cgroups.
2. Imagem & DockerfileCamadas, instruções e multi-stage build.
3. Dados & RedeVolumes, bridge/host e Docker Compose.
📦
Analogia do dia: uma VM é uma casa inteira com sua própria caixa d'água, padrão de luz e encanamento. Um Container é um apartamento num prédio: cada um tem suas paredes e chave (namespaces) e seu limite de consumo (cgroups), mas todos usam a mesma fundação e encanamento do prédio (o kernel do host).
ARQUITETURA

Máquina Virtual × Container

Containers isolam processos usando recursos do kernel Linux: namespaces (isolamento de PID, rede, sistema de arquivos, usuários) e cgroups (controle e limite de CPU, memória e I/O).
IMAGEM × CONTAINER

Receita congelada × Bolo em execução

Imagem Docker

Modelo imutável e somente leitura formado por camadas empilhadas (UnionFS). Fica salva num Registry (Docker Hub, Harbor).

Mesma imagem pode gerar vários containers.

Container

Instância em execução da imagem + uma camada gravável fina no topo.

Se o container for removido, o que foi gravado nessa camada efêmera some!

Imagens são construídas em camadas cacheadas: se uma linha do Dockerfile não mudou, o Docker reaproveita o cache daquela camada.
DOCKERFILE

As instruções que caem em prova

FROM eclipse-temurin:21-jre-alpine   # imagem base
WORKDIR /app                        # diretório de trabalho
COPY target/app.jar app.jar         # copia arquivos locais (preferir ao ADD)
ENV SPRING_PROFILES_ACTIVE=prod     # variável em runtime
EXPOSE 8080                         # documenta a porta (não publica sozinha!)
RUN addgroup -S app                 # roda no BUILD da imagem
ENTRYPOINT ["java","-jar","app.jar"] # processo principal ao iniciar
ParDiferença-chave para a FGV
RUN × CMDRUN executa no build (grava camada); CMD define o comando padrão ao iniciar o container.
CMD × ENTRYPOINTCMD é facilmente sobrescrito por argumentos no docker run; ENTRYPOINT fixa o executável (e o CMD vira argumento dele).
COPY × ADDCOPY só copia local→imagem; ADD também descompacta .tar e baixa URL (use COPY por padrão).
BOAS PRÁTICAS

Multi-stage Build: imagem leve e segura

PERSISTÊNCIA E REDE

Volumes e Redes no Docker

Onde salvar dados persistentes?
  • Named Volume (-v dados:/var/lib/pg): gerenciado pelo Docker; ideal em produção.
  • Bind Mount (-v ./src:/app): espelha pasta exata do host; ótimo em dev.
  • tmpfs: só na RAM; some ao parar o container.
Tipos de Rede
  • bridge: padrão; rede virtual isolada no host (containers conversam por nome em bridge customizada).
  • host: remove isolamento de rede; usa direto o IP/portas do host.
  • none: sem interface de rede.
  • overlay: conecta containers entre múltiplos hosts (Swarm).
MULTI-CONTAINER

Docker Compose (compose.yml)

Em vez de digitar vários docker run compridos, você descreve a pilha inteira num YAML e sobe com docker compose up -d.

services:
  api:
    build: .
    ports: ["8080:8080"]
    depends_on: [db]      # ordem de inicialização (não espera o banco estar "pronto" sem healthcheck!)
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
volumes:
  pgdata:
Docker Compose cria automaticamente uma rede bridge para os serviços do arquivo se enxergarem pelo nome do serviço (ex.: db).
PEGADINHA

Pegadinhas clássicas de Docker

✗ “EXPOSE 8080 no Dockerfile já publica a porta no host.” ✓ EXPOSE é apenas documentação. Para publicar de verdade, use -p 8080:8080 no docker run ou ports: no Compose.
✗ “depends_on: [db] garante que o PostgreSQL já terminou de inicializar antes da API subir.” ✓ Sem condition: service_healthy + healthcheck, o Compose só espera o container iniciar, não a porta estar pronta.
RESUMO

Capítulo 3 numa colinha

Container = Kernel compartilhado + namespaces (isola) + cgroups (limita).Imagem é imutável em camadas; dados duráveis vão em Volumes.
  • VM virtualiza hardware e SO completo; container compartilha o kernel do host.
  • RUN roda no build; CMD/ENTRYPOINT rodam no start do container.
  • Multi-stage build reduz tamanho e superfície de ataque da imagem final.
  • Named volume (gerenciado) e bind mount (caminho do host) persistem dados.
  • Rede bridge isola; host compartilha rede do servidor; none desliga rede.
  • Docker Compose orquestra múltiplos serviços, redes e volumes declarativamente.
TESTE RÁPIDO

Pense antes de abrir

1) Qual recurso do Linux impede que um container consuma 100% da RAM do servidor?

cgroups (Control Groups) Enquanto namespaces isolam o que o processo vê, cgroups limitam CPU, memória e I/O.

2) Se você apagar um container que rodava um banco sem volume configurado, o que acontece com os dados?

São perdidos Os dados estavam na camada gravável efêmera do container.

3) Qual a diferença entre COPY e ADD no Dockerfile?

COPY só copia arquivos locais ADD faz o mesmo, mas também baixa URLs remotas e extrai arquivos compactados (.tar) automaticamente.

4) Na rede host, é necessário mapear portas com -p 8080:8080?

Não O container compartilha diretamente a pilha de rede e as portas do próprio host.

Kubernetes (K8s)

☸️
1. ArquiteturaControl Plane e Worker Nodes.
2. Cargas & RedePod, Deployment, Service e Ingress.
3. ConfiguraçãoConfigMaps e Secrets (cuidado com Base64!).
🚢
Analogia do dia: se o Docker é o contêiner de carga, o Kubernetes é o porto automatizado inteiro: ele decide em qual navio (Nó) colocar cada caixa (Pod), substitui caixas que caíram no mar (Deployment) e direciona os caminhões até o portão certo (Service/Ingress).
ARQUITETURA DO CLUSTER

Control Plane × Worker Nodes

Todos os componentes falam com o etcd apenas através do kube-apiserver. O kubelet garante que os containers dos Pods estejam rodando no nó.
CARGA DE TRABALHO

Pod, ReplicaSet e Deployment

Deployment→ReplicaSet→Pods (réplicas)
  • Pod: menor unidade implantável no K8s. Agrupa 1 ou mais containers que dividem o mesmo IP (localhost entre eles) e volumes. É efêmero: se morrer, nasce outro com outro IP.
  • ReplicaSet: mantém o número desejado de réplicas de um Pod (ex.: sempre 3).
  • Deployment: objeto que você cria no dia a dia. Gerencia ReplicaSets para fazer rolling updates sem queda e rollback fácil para versão anterior.
Na prática, não se cria Pods avulsos em produção: cria-se um Deployment (stateless) ou StatefulSet (com identidade/armazenamento persistente).
REDE INTERNA E EXTERNA

Services: dando endereço fixo para Pods efêmeros

Como Pods morrem e mudam de IP, o Service usa seletores de rótulos (labels) para criar um IP e DNS estáveis e balancear carga entre os Pods saudáveis.

Tipo de ServiceQuem acessaComo funciona
ClusterIP (padrão)Só dentro do clusterCria um IP virtual interno (ex.: comunicação API → Banco).
NodePortExterno (porta alta)Abre a mesma porta (30000–32767) em todos os nós do cluster.
LoadBalancerExterno (Internet)Provisiona um balanceador externo no provedor de nuvem.
ExternalNameInterno → DNS foraMapeia o Service para um nome DNS externo (CNAME).
CAMADA 7 (HTTP/HTTPS)

Ingress: o porteiro inteligente

Ingress não é um tipo de Service: ele é um objeto de roteamento HTTP/HTTPS (camada 7) que exige um Ingress Controller (ex.: NGINX, Traefik) para funcionar.
CONFIGURAÇÃO

ConfigMap × Secret

ConfigMap

Guarda configurações não sensíveis (URLs, feature flags, arquivos application.properties) separadas da imagem.

Entra no Pod como variável de ambiente ou arquivo montado.

Secret

Guarda dados sensíveis (senhas, tokens, certificados TLS).

Armazenado em Base64 por padrão — isso é codificação, NÃO criptografia!

# Qualquer um decodifica Base64 sem chave nenhuma:
echo "c2VuaGExMjM=" | base64 -d   # → senha123
EXEMPLO YAML

Lendo um manifesto declarativo

apiVersion: apps/v1
kind: Deployment
metadata: { name: pje-api }
spec:
  replicas: 3                 # estado desejado
  selector:
    matchLabels: { app: pje } # casa com os Pods
  template:
    metadata:
      labels: { app: pje }
    spec:
      containers:
        - name: api
          image: registry.tjpb/pje:1.4

Se um Pod cair, o controller-manager vê que só há 2 de 3 e manda criar outro automaticamente.

PEGADINHA

Onde a FGV pega em Kubernetes

✗ “Kubernetes Secrets criptografam senhas com Base64.” ✓ Base64 é apenas codificação reversível. Segurança real exige RBAC restrito + Encryption at Rest no etcd (ou cofre externo como Vault).
✗ “O Service LoadBalancer roteia por caminho /api e /web.” ✓ Services operam na camada 4 (TCP/UDP). Roteamento HTTP por host/path é papel do Ingress.
✗ “O kubelet fica no Control Plane.” ✓ kubelet e kube-proxy rodam nos Worker Nodes.
RESUMO

Capítulo 4 numa colinha

Deployment garante Pods; Service dá IP fixo; Ingress roteia HTTP.Control Plane (apiserver, etcd, scheduler, controller-manager) × Worker (kubelet, kube-proxy).
  • etcd guarda todo o estado do cluster; só o kube-apiserver fala direto com ele.
  • Pod é efêmero; containers do mesmo Pod dividem IP e volumes.
  • ClusterIP (interno), NodePort (porta no nó), LoadBalancer (externo L4).
  • Ingress roteia L7 (host/path/TLS) e precisa de Ingress Controller.
  • ConfigMap = dados comuns; Secret = dados sensíveis (Base64 ≠ criptografia!).
TESTE RÁPIDO

Pense antes de abrir

1) Qual componente do Control Plane decide em qual Worker Node um novo Pod será colocado?

kube-scheduler Ele avalia recursos disponíveis, afinidade e restrições para escolher o melhor nó.

2) Dois containers dentro do mesmo Pod querem conversar via HTTP. Qual endereço usam?

localhost (127.0.0.1) Containers de um mesmo Pod compartilham o mesmo namespace de rede.

3) Você quer expor 5 serviços HTTP diferentes sob um único domínio e certificado TLS. O que usar?

Ingress Roteia por host/path (camada 7) para cada Service ClusterIP interno.

4) Por que não basta criar um Secret para garantir sigilo absoluto de uma senha no cluster?

Base64 é só codificação Sem RBAC e criptografia em repouso no etcd, quem lê o objeto decodifica a senha facilmente.

INFRAESTRUTURA COMO CÓDIGO

Terraform: declarativo e idempotente

Em vez de clicar no console da nuvem, você descreve a infra em arquivos .tf (linguagem HCL). Se rodar de novo sem mudar nada, ele não duplica servidores (idempotência).

Blocos principais do HCL
  • provider: conecta à nuvem (AWS, Azure, GCP, K8s).
  • resource: cria/gerencia um recurso real.
  • data: apenas lê um recurso que já existe.
  • module: empacota recursos reutilizáveis.
Ciclo de vida
init→plan→apply→destroy

init baixa providers; plan mostra o diff antes de mexer; apply executa; destroy apaga tudo.

TRACING NA PRÁTICA

Como um Trace acha o gargalo

Trace ID: 9f8a-12bc (Requisição total: 850 ms)
├─ Span 1: API Gateway         [ 20 ms ]
├─ Span 2: Serviço de Processo [800 ms]  ← GARGALO!
│  └─ Span 3: Query PostgreSQL [740 ms]
└─ Span 4: Serviço de Log      [ 30 ms ]

Cada serviço propaga o cabeçalho do Trace ID. Sem tracing distribuído, você só saberia que "o sistema está lento", sem saber qual microsserviço travou.

IaaS dá VM; PaaS dá plataforma; SaaS dá software. Terraform usa tfstate.Observabilidade = Métricas (Prometheus) + Logs (ELK/OpenSearch) + Traces (APM).
  • IaaS: você gerencia SO/runtime/app; PaaS: você gerencia app/dados; SaaS: tudo é do provedor.
  • Terraform é declarativo e idempotente; ciclo init → plan → apply → destroy.
  • tfstate mapeia .tf para recursos reais; em equipe exige backend remoto + lock.
  • Prometheus coleta métricas por pull; Zabbix monitora infra/SNMP; Grafana cria painéis.
  • ELK / OpenSearch centralizam logs; Tracing (Trace/Span ID) rastreia requisições entre serviços.

Pense antes de abrir

1) Você sobe apenas o código Python e o provedor cuida do SO, runtime e escala. Esse modelo é:

PaaS (Platform as a Service) O desenvolvedor foca apenas na aplicação e nos dados.

2) Qual comando do Terraform mostra as mudanças previstas na nuvem sem alterar nada ainda?

terraform plan Ele compara o código .tf com o estado real (tfstate) e exibe o plano de execução.

3) Na stack ELK, qual componente armazena e indexa os logs para busca rápida?

Elasticsearch Logstash coleta/transforma e Kibana exibe os gráficos e buscas.

4) Qual pilar da observabilidade usa Trace ID e Spans para localizar lentidão entre microsserviços?

Tracing distribuído (APM) Mostra exatamente quanto tempo cada chamada levou em cada serviço.
