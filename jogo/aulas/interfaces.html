CÓDIGO SEGURO

Errado vs Certo no armazenamento de sessão

// ERRADO: texto plano em XML do app
prefs.edit().putString("access_token", jwt).apply()

// CERTO (Android): chave protegida pelo hardware Keystore
val encrypted = EncryptedSharedPreferences.create(
  context, "secure_auth", masterKey,
  PrefKeyEncryptionScheme.AES256_SIV,
  PrefValueEncryptionScheme.AES256_GCM
)
encrypted.edit().putString("access_token", jwt).apply()
ARMADILHA OFFLINE

O que NUNCA deixar desprotegido no aparelho

Riscos

Backup automático na nuvem vazando banco local, SQLite sem SQLCipher para dados sigilosos e logs de debug com CPF/token no Logcat.

Contramedidas

Desabilitar allowBackup para arquivos sensíveis, cifrar segredos em Keychain/Keystore e limpar cache ao encerrar sessão.

SYNC OFFLINE

Offline-first e sincronização resiliente

Apps de campo/auditoria sincronizam fila local com o servidor quando volta a rede.

  • Use WorkManager (Android) / BGTaskScheduler (iOS) em vez de serviços em loop consumindo bateria.
  • Exija chaves de idempotência (UUID por operação) para evitar duplicidade se o envio repetir por timeout.
  • Use ETag / If-None-Match para economizar banda móvel.
RESUMO DO CAPÍTULO

Checklist Mobile essencial

  • Activity coberta parcialmente → onPause(); totalmente oculta → onStop().
  • ViewModel segura estado UI sem memory leak na rotação.
  • Token/credencial = Keystore / Keychain; dado relacional = Room / Core Data / SQLite.

CAPÍTULO 2

Segurança Mobile, SSL Pinning, REST/JSON e Push

🔐
1. Engenharia reversaAPK/IPA é legível no cliente: nunca embuta segredos.
2. SSL/TLS PinningBloquear MITM e rotacionar chaves sem quebrar o app.
3. Rede mobileTimeout, retry idempotente e paginação leve.
4. Push FCM/APNsNotificação como gatilho sem vazar dados na tela bloqueada.
OWASP MASVS

O cliente móvel é ambiente hostil

Quem baixa o APK/IPA pode descompilá-lo (jadx, Frida) ou rodar em aparelho com root/jailbreak.

Verdade absoluta de prova: Ofuscação (ProGuard/R8) apenas dificulta leitura; autorização, validação de permissões e chaves privadas de API ficam SEMPRE no servidor!
SSL / TLS PINNING

Barrando proxy interceptador (MITM)

Fixe o hash da chave pública (SPKI) + uma chave de backup, não apenas o certificado folha que vence rápido.

NETWORK SECURITY CONFIG

Configuração declarativa no Android

<network-security-config>
  <domain-config cleartextTrafficPermitted="false">
    <domain includeSubdomains="true">api.tjpb.jus.br</domain>
    <pin-set expiration="2027-06-01">
      <pin digest="SHA-256">BASE64_SPKI_ATUAL=</pin>
      <!-- Pino reserva obrigatorio para rotacao -->
      <pin digest="SHA-256">BASE64_SPKI_BACKUP=</pin>
    </pin-set>
  </domain-config>
</network-security-config>
REST / JSON NO CELULAR

Boas práticas em redes móveis instáveis

Problema MobileSolução Técnica

PUSH (FCM / APNS)

Fluxo seguro de notificação Push

Por quê? O payload do push passa por servidores terceiros (Google/Apple) e aparece na tela bloqueada. Nunca coloque CPF, valor ou teor sigiloso no push!

PKCE NO MOBILE

OAuth 2.0 + OIDC com PKCE em apps nativos

App nativo é cliente público (não consegue guardar client_secret). Por isso a RFC 7636/8252 exige Authorization Code + PKCE usando o navegador do sistema (Custom Tabs / ASWebAuthenticationSession), nunca WebView embutida.

RESUMO DO CAPÍTULO

Checklist de Rede & Segurança Mobile

  • Zero segredo hardcoded no APK/IPA.
  • SSL Pinning por SPKI + chave backup.
  • Push envia só referência opaca; app busca conteúdo autenticado via HTTPS.
TREINO FGV

Validação rápida — Cap. 2

1. Por que pinar SPKI em vez de apenas o certificado final?

Se a chave pública for mantida (ou houver pino de backup), o app não para de funcionar durante a renovação rotineira do certificado no servidor.

2. Por que app mobile deve usar Custom Tabs / Safari View + PKCE?

Porque apps móveis são clientes públicos sem client_secret seguro e WebView interna permitiria ao app espionar a senha digitada no login.

MOBILE-FIRST VS DESKTOP-FIRST

CSS que cresce com min-width

/* MOBILE-FIRST: base para telas pequenas (1 coluna) */
.grid { display: grid; grid-template-columns: 1fr; gap: 1rem; }

/* Tablet em diante */
@media (min-width: 768px) { .grid { grid-template-columns: repeat(2, 1fr); } }

/* Desktop */
@media (min-width: 1200px) { .grid { grid-template-columns: repeat(3, 1fr); } }
Desktop-First faz o caminho inverso usando max-width decrescente.

USABILIDADE

Heurísticas essenciais de Nielsen na prática

Feedback & Prevenção

Visibilidade do status (loading/sucesso), prevenção de erro antes de confirmação destrutiva e mensagens de erro claras com ação corretiva.

Consistência & Reconhecimento

Ícones e rótulos padrão em todo o sistema; reconhecer em vez de obrigar o usuário a memorizar códigos entre telas.

DESIGN RESPONSIVO

Cuidados de viewport e tipografia

  • Sempre inclua <meta name="viewport" content="width=device-width, initial-scale=1">.
  • NUNCA trave zoom com user-scalable=no — é barreira grave de acessibilidade para baixa visão!
  • Prefira unidades rem/em e layouts flexíveis em Grid/Flexbox sem pixels rígidos horizontais.

  • Mobile-First = CSS base pequeno + @media (min-width: ...).

Seção 4.2 — Folha de Alto Contraste

Regra literal do eMAG 3.1: A folha de alto contraste exige razão mínima de 7:1: fundo #000000, texto #FFFFFF, links sublinhados em amarelo #FFF333, ícones e bordas em branco.

MARCAÇÃO E LINKS

Recomendações que caem direto em questões

Evite

Links com texto genérico "clique aqui" ou "saiba mais" isolados; pular de <h1> para <h4>; abrir nova aba sem avisar o usuário (Rec. 1.9).

Prefira

Texto descritivo ("Baixar Edital TJPB (PDF, 420 KB)"); hierarquia contínua h1→h2→h3; aviso prévio quando abrir nova janela.

FORMULÁRIOS NO EMAG

Seção 3.6 — Dados sem barreira

  • Botão de imagem (type="image") exige texto alternativo (Rec. 6.1).
  • Todo campo precisa de <label for="..."> explícito (não use apenas placeholder, que some ao digitar).
  • Em envios críticos/irreversíveis, exiba tela de confirmação/revisão para o usuário conferir antes do envio final.
AVALIAÇÃO

Como validar um portal segundo o eMAG

O próprio eMAG define fluxo em 2 etapas: (1) validadores automáticos (ex.: ASES/axe) + (2) avaliação humana com checklist, navegação apenas por teclado (Tab/Shift+Tab/Enter/Esc) e leitores de tela reais.

RESUMO DO CAPÍTULO

Checklist eMAG 3.1

  • Atalhos padrão: 1-Conteúdo · 2-Menu · 3-Busca.
  • Alto contraste mínimo 7:1 (fundo preto, texto branco, links #FFF333 sublinhados).
  • Validador automático NÃO substitui teclado + leitor de tela + revisão humana.

1ª REGRA DA ARIA

HTML5 nativo ganha de <div role="...">

<!-- CERTO: foco por Tab, Enter/Espaco e leitor prontos -->
<button type="button" onclick="salvar()">Salvar petição</button>

<!-- FRAGIL: ARIA NAO adiciona Tab nem clique por Enter! -->
<div role="button" tabindex="0" onclick="salvar()"
     onkeydown="if(event.key==='Enter'||event.key===' ')salvar()">Salvar</div>

Landmarks nativos: <header>, <nav>, <main>, <aside>, <footer>.

TREINO FGV

Validação rápida — Cap. 5

1. Qual a diferença de efeito entre tabindex="0" e tabindex="-1"?

0 coloca o elemento no fluxo normal do Tab; -1 tira do Tab mas permite elemento.focus() via script.

2. O critério 3.3.8 (Accessible Authentication) proíbe o quê?

Proíbe exigir testes cognitivos (memorizar senha sem poder colar, resolver captcha visual/puzzle) sem fornecer alternativa como passkey, copy-paste ou suporte a gerenciador de senhas.
